# 个人维护与 Codex 协作

你已能读代码和操作 Git，下一步优先掌握需求取舍、测试断言和验收证据。用地点聚合器练习：你决定用户行为与优先级，Codex 执行范围内的实现、调试和验证。

## 一次任务怎么开始

简单改动直接描述目标；跨模块或存在重要取舍时先使用 Plan。提供具体例子比“高质量完成”更有帮助：

```text
目标：第二页加载失败后，用户能够重试。
约束：沿用现有 API 和分页限制。
验收：首批 25 条保持；失败有提示；重试成功追加新地点；重复地点去重。
请检查当前代码与测试，完成实现和适用验证，报告结果及待验收项。
```

开始时检查工作区、分支、HEAD 和已有修改。使用适合任务的干净工作区；新工作区应能从锁文件安装、准备测试环境并运行检查。常用入口写在仓库命令中，项目指令只说明如何选择。

## 哪些交给 Codex，哪些由你判断

| 工作 | Codex 的责任 | 你重点看什么 |
| --- | --- | --- |
| 需求 | 澄清歧义、列验收例子 | 是否解决真实问题，是否遗漏重要行为 |
| 设计 | 比较方案与维护成本 | 新依赖和复杂度是否值得 |
| 实现 | 小范围改动、保留现有行为 | diff 是否符合目标 |
| 测试 | 编写并执行，定位失败 | 断言是否表达需求，坏实现能否被捕获 |
| 调试 | 给出复现、根因和修复证据 | 结论是否得到运行结果支持 |
| 审查 | 从验收和风险重新检查差异 | 异常、取消、数据隔离是否遗漏 |
| 发布 | 准备对应版本与检查证据 | 产品体验、剩余风险和发布取舍 |

Codex 容易沿用错误前提、漏异常路径、为当前实现写出同样有误的测试，或增加过多抽象。审查时明确要求挑战这些假设，检查关键断言，而非只看通过数量。

## 日常验证怎么选

| 变更 | 适用验证 |
| --- | --- |
| 核心逻辑、Route | `npm test`、`npm run test:api`、类型检查和构建 |
| 页面交互、状态、分页、回放 | 上述检查 + `npm run test:acceptance` |
| 历史 API、Cookie、Prisma | 上述检查 + `npm run test:history:integration` |
| 准入、事务、SQL、连接池 | 上述检查 + `npm run test:admission:postgres` |

准备与命令见 [测试说明](../test/README.md)。浏览器测试使用真实生产页面与受控 API；历史集成使用真实 Next Route、Prisma、独立 PostgreSQL，并以 SQL 查询核实写入和删除。真实高德与 Vercel 断连验收继续按具体任务预算执行。

你可以让 Codex 演示一个失败场景：临时破坏关键行为，确认对应测试失败，查看报告，再恢复实现并通过验证。修改测试期望需要需求依据；偶发失败应先定位复现条件。

## 看交付时的五个问题

1. 改动解决了哪个具体现象？是否符合本次范围？
2. 审查、测试与部署对应哪个提交？本地补丁基于哪个 SHA？
3. 哪些验收例子已有自动测试，哪些做了人工验证？
4. 失败能否通过日志、请求或 trace 定位？
5. 还有哪些待验收项，是否影响这次交付？

建议交付格式：问题与结果；基线与差异；验证命令和实际结果；证据位置；剩余待办。沿用 PR 模板，按任务长度调整。

## 值得练习的 Codex 功能

- Plan：用于复杂取舍，先确认目标和行为；简单任务直接实现。
- diff 与行内评论：针对具体代码和风险反馈，例如“这里取消后是否仍会保存旧搜索？”
- Worktree 与本地环境：隔离任务，并验证初始化动作和运行命令可重复。
- 浏览器与 DevTools：检查成功、空、加载、失败等状态，以及控制台和请求。
- AGENTS.md：保存稳定的项目规则与命令选择；重复步骤成熟后再提炼成 skill。

官方参考：[项目与环境](https://learn.chatgpt.com/docs/projects)、[浏览器](https://learn.chatgpt.com/docs/browser)、[项目指令](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

## 工具与投入取舍

| 工具／投入 | 当前用途 | 后续选择条件 |
| --- | --- | --- |
| Playwright Test | 固定场景、CI、HTML 报告和失败 trace | 已接入 Chromium，随关键行为增加回归 |
| 现有浏览器／DevTools | 探索、复现和性能检查 | 页面或请求出现难复现问题时使用 |
| `ecc:e2e-testing` | 测试组织参考 | 按需调用，API 用法核对锁定版本文档 |
| 调试／审查 skills | 帮助执行有明确目标的检查 | 选择任务相关的一项，减少流程重叠 |
| Vercel 插件 | 平台与部署查询候选 | 经常需要查部署信息时评估接入 |
| Playwright Test Agents | 探索、生成和修复用例 | 现有套件稳定后评估，审查生成断言 |

本轮轻量投入包括协作规则、浏览器回归、历史业务集成和 CI 证据。扩展投入可增加跨浏览器、请求关联与错误监控、发布后业务检查和回退演练；依据用户量、事故和定位成本逐项安排。评估收益采用回归是否被发现、复现是否稳定、定位是否更快等证据。

参考：[Playwright CI 与报告](https://playwright.dev/docs/ci-intro)、[测试实践](https://playwright.dev/docs/best-practices)、[Test Agents](https://playwright.dev/docs/test-agents)。

验收证据统一记录源码指纹和执行结果，见 `test-results/evidence/`；浏览器 HTML 报告包含通过场景截图和合成请求，失败场景包含 trace。交付链接指向本次实际结果。
