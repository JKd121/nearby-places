# v0.1B-2B Plan

Status: `AWAITING_PLAN_APPROVAL`

This is a plan-only document. It does not authorize implementation in this turn.

## 1. Current UI review

The stable B-2A page already provides the complete interaction surface: resolve/confirm, category selection, grouped toggles, all/clear, radius, search, filters, sorting, local reveal, and partial-success states. The visual implementation is intentionally functional and currently lives mainly in `src/web/SearchApp.tsx` and `app/globals.css`.

Current observations:

- The `h1` uses a large `clamp` range and consumes more first-screen height than a daily-use search tool needs.
- `search-panel`, `location-confirmation`, and `controls-panel` read as several stacked cards rather than one compact control area.
- Category checkboxes are semantically correct but visually close to a plain form list; group/category hierarchy is not immediate at a glance.
- Radius options look like independent pills instead of one segmented control.
- The primary actions and secondary actions have similar visual weight in some widths.
- The resolved location is clear but can use a smaller inline confirmation treatment with coordinates de-emphasized.
- Results summary, filters, and sort are functional but not yet a single compact toolbar.
- Filter buttons are larger than necessary for desktop scanning.
- A place row has the right fields, but name, distance, rating, cost, tags, and address need stronger hierarchy and more predictable wrapping.
- Long addresses can make rows unnecessarily tall; tags and addresses need restrained line treatment.
- Loading is text-only. Error and empty states work but need the same spacing and border language as results.
- Mobile has a basic 640px media query and a local filter scroller, but the page should be deliberately checked at 375/390/430px rather than treated as a narrow desktop layout.

## 2. Identified visual problems

The B-2B work should address density and clarity, not add behavior:

1. Reduce title scale and header spacing so the location/search controls appear quickly.
2. Replace the impression of large stacked cards with a quiet page surface, subtle control boundaries, and clear section labels.
3. Make selected categories and group state visually obvious without removing native checkbox semantics.
4. Present radius as one compact segmented control with one selected segment.
5. Keep “解析地点” and “搜索附近” primary, while making “修改地点”, “全选”, “清空”, and “加载更多” quieter.
6. Bring result summary, filters, and sort into one responsive toolbar.
7. Establish a row anatomy that makes name and distance easiest to scan, followed by rating/cost, tags, and address.
8. Clamp long address text to one or two lines without hiding the whole location context.
9. Use consistent muted treatment for null rating/cost, empty, error, and loading states.
10. Ensure mobile controls wrap or scroll locally and never create page-level horizontal overflow.

## 3. Target visual direction

The target is a compact, restrained, information-dense location search tool. Use a quiet background, white or near-white surfaces, thin borders, small radii, one teal accent, and modest type contrast. There should be no gradient, glass effect, glow, dashboard sidebar, oversized hero, floating cards, or decorative animation. Rows should feel like a fast list, not a collection of marketing cards.

The existing functional component tree is sufficient. B-2B should primarily adjust class names/markup where needed and CSS. Search semantics, request payloads, result derivation, and all existing state transitions remain unchanged.

## 4. Design tokens

Keep a small plain-CSS token set in `:root`:

```css
--bg: #f4f6f7;
--surface: #ffffff;
--surface-subtle: #f7f9fa;
--text: #18212b;
--text-muted: #66737f;
--border: #d9e1e6;
--accent: #176b87;
--accent-hover: #125a72;
--danger: #a33b36;
--radius-sm: 6px;
--radius-md: 10px;
```

Use existing system font stacks. Do not introduce a design-system package or a second color palette. Focus, selected, error, and disabled states should derive from these tokens with modest opacity changes.

## 5. Typography hierarchy

- Product title: approximately 1.7–1.9rem desktop, 1.35–1.5rem mobile, weight 650 rather than a landing-page headline.
- Section title: 1.05–1.2rem, weight 650.
- Control label/group label: .8–.9rem, weight 650; avoid excessive uppercase treatment for Chinese text.
- POI name: 1rem desktop/mobile, weight 600; one line where possible.
- Distance: .9rem, accent or text color, stable position at the end of the name row.
- Rating/cost/category metadata: .82–.9rem, normal or medium weight.
- Tag: .8–.85rem, muted accent; never stronger than the POI name.
- Address/helper text: .78–.85rem, muted; line-height around 1.45.

Line height should favor scanning, not oversized breathing room. Do not use heavy font weight on every row.

## 6. Desktop layout

At 1280px and 1440px, keep the page content near 960–1040px and centered. Use page padding around 28–36px vertically. The header is compact, followed by a control region with a clear but light border. Avoid wrapping the whole page in one giant card.

The desktop control layout should read as:

```text
地点   [ input ................................ ] [解析地点]
       已定位：深圳北站 · 深圳市龙华区                 [修改]
类别   [group/category controls]
范围   [1 km | 2 km | 3 km | 5 km]                  [搜索附近]

附近结果 · count/status     [filters........................]  排序 [select]
---------------------------------------------------------------
POI rows
```

Controls may use a two-column or inline grid where it reduces height, but labels must remain associated with their controls. The result area should begin soon after search and show several rows per screen.

## 7. Mobile layout

At 375px, 390px, and 430px:

- Use roughly 12–16px page padding.
- Make the input full width; put the resolve button below or beside it only when it remains comfortably tappable.
- Let category chips wrap naturally; do not shrink text to fit eight items on one line.
- Keep radius as a full-width or wrapped segmented control with touch-friendly segments.
- Stack the search action after the controls with a clear but not oversized button.
- Let the filter strip scroll horizontally inside its own container; the document itself must not scroll horizontally.
- Allow the result toolbar to wrap summary, filters, and sort into separate rows.
- Use one-column rows; keep name/distance on a stable first line and let metadata wrap below.
- Clamp addresses to two lines and preserve enough text to understand the area.
- Keep load more full-width or comfortably centered, with a quiet secondary treatment.

Mobile must not depend on hover, absolute positioning, or desktop-only row alignment.

## 8. Search controls design

Keep the existing two-stage flow and labels. Visually group the resolved location and search controls without making each a large independent card. The location input remains the first focusable control. “解析地点” is the primary action for the first phase; “搜索附近” is the primary action after confirmation. Loading changes the button label as today, but the button should not become a giant banner.

Category, radius, and search controls should share spacing and border tokens. A short helper line can explain “已选 N 类 · X km” if useful, but no new state or request behavior is introduced.

## 9. Category selector design

Keep native checkbox inputs and the current group semantics. Style each category as a compact selectable chip/label with:

- clear selected background/border;
- quiet unselected surface;
- visible keyboard focus;
- disabled opacity only when the existing search phase disables interaction.

Group labels should be visually stronger than their member chips. The group toggle remains a button with its current select/clear behavior; use text and a subtle state indicator, not eight oversized buttons. Do not copy typecodes or AMap fields into markup.

## 10. Radius design

Style the four existing radio labels as one segmented control. The selected segment uses the accent token and sufficient contrast; unselected segments use the surface-subtle/border tokens. Keep the underlying radio semantics and keyboard behavior. No new radius values or automatic search are introduced.

## 11. Resolved-location design

Use a compact confirmation strip:

```text
已定位
深圳北站（兴趣点） · 深圳市龙华区                         修改
114.025796, 22.608443
```

The matched address/name is primary, administrative context is secondary, and coordinates are small muted text. Keep the existing “修改地点” action and its invalidation semantics. Do not add a map or details panel.

## 12. Results toolbar

The summary, filter controls, and sort select should share one toolbar region with a single visual hierarchy. The summary leads, filters are compact tabs/pills, and sort is a secondary labeled control. On desktop they may sit on one row; on mobile they may wrap in this order: summary, filters, sort.

Do not make “全部” a large CTA. Keep category error/empty text indicators visible and understandable without relying on color alone.

## 13. Filter design

Keep the existing local-only filter buttons and `role="tab"` behavior. Reduce padding and font size slightly on desktop, retain comfortable touch targets on mobile, and show selected state through border/background plus `aria-selected`. The filter strip may scroll horizontally only within its own container. Error/empty categories remain present with short text markers such as “失败” or “空”.

## 14. Sort design

Keep the existing `<label>` and `<select>` semantics, allowed-mode calculation, sort fallback, and no-request behavior. Style it as a quiet compact select. It must not visually outrank the location, category, or search controls. When the toolbar wraps on mobile, the select should fit the content width without overflowing.

## 15. POI row anatomy

Use a dense list row, not a card with elevation:

```text
POI name                                             1.1 km
火锅 · ★ 4.6 · 人均 ¥95
牛肉 · 双人餐
深圳市龙华区……
```

Name and distance are the strongest line. Rating/cost follow the existing category policies. Tags use muted accent text and remain secondary. Address uses muted text with `overflow-wrap` and a one/two-line clamp. Keep separators clear with a thin border and optional very subtle hover background only; rows are not clickable and must not get fake lift/cursor affordances.

## 16. Loading/error/empty design

Keep the existing serial-search text and do not invent percentages. Add a small CSS spinner or non-animated progress marker only if it can remain unobtrusive; no 200-row skeleton. Loading should use the same muted helper spacing as the rest of the page.

Errors should be compact text with a danger border or icon/text cue, never a full-screen red alert. Empty states should use the same surface and muted type language. Partial success continues to show successful rows and a concise summary such as “7 个类别成功 · 1 个失败”.

## 17. Accessibility changes

- Preserve the existing location `label`, fieldsets, legends, checkbox/radio semantics, button semantics, and select label.
- Add or verify visible `:focus-visible` styles for every interactive control, including chips, group actions, filters, and load more.
- Ensure group mixed state is conveyed by text/attribute as well as styling; do not rely on color alone.
- Keep `aria-busy` during resolving/searching and `aria-live` for summaries, loading, errors, and empty states.
- Keep `aria-selected` on filters and `aria-pressed`/equivalent state on group actions accurate.
- Ensure disabled controls remain legible and are not the only indication of a state.
- Check contrast for muted text, selected pills, danger text, and focus rings.
- Preserve keyboard order: location → resolve → category groups/categories → radius → search → result filters → sort → load more.
- Avoid hover-only information and avoid adding motion that users cannot turn off.

No accessibility library is planned.

## 18. Responsive breakpoints

- Base styles: mobile-first rules that work at 375px.
- `max-width: 640px`: control stacking, toolbar wrapping, one-column result rows, compact title, and local filter scrolling.
- `max-width: 430px`: reduce page padding and row gaps; ensure radius segments and sort select remain tappable.
- `max-width: 375px`: verify no fixed-width chip, button, address, or toolbar causes document overflow.
- Desktop styles should remain constrained at 1280px and 1440px through the existing max-width rather than expanding row width indefinitely.

## 19. Component changes

Do not create a new design-system layer or ten small components. `SearchApp.tsx` already contains `CategorySelector`, `ResultsView`, and `PlaceList`; keep those boundaries and adjust their markup/classes in place. Only extract `ResultsToolbar` or `PlaceRow` if a concrete readability problem makes the current file hard to review. No state, request, result, or sorting logic moves to a new architecture.

## 20. CSS changes

Limit implementation to `app/globals.css` plus the minimum className/semantic markup adjustments in `src/web/SearchApp.tsx`:

- replace/extend the small token set;
- reduce header and panel height;
- style compact category chips and one radius segmented control;
- align summary/filter/sort toolbar;
- improve dense row hierarchy, separators, tag/address wrapping;
- add consistent loading/empty/error treatment;
- add focused 640/430/375 responsive rules;
- add only restrained 100–180ms state transitions if they improve selected/focus feedback, with `prefers-reduced-motion` support.

Do not rewrite the AMap/search core, API routes, request contract, dedupe, load-more algorithm, radius values, or stale logic.

## 21. Files affected

Expected scope:

- Modify `app/globals.css`.
- Modify `src/web/SearchApp.tsx` only for visual classes, semantic attributes, or component markup that does not alter behavior.
- Optionally add no new component file; split only if the existing file becomes materially harder to review.
- Do not change `src/web/logic.ts`, AMap code, search service, API routes, or tests for business behavior.
- Add/update a screenshot checklist artifact under `harness/build/` only if the implementation workflow needs to record manual review; do not add screenshot tooling as a product dependency.

## 22. Implementation stages

B-2B should remain one bounded implementation phase, not another product split. Within that phase use three reviewable passes:

1. Tokens and layout: compact header, control surfaces, category/radius treatments, desktop/mobile base.
2. Results presentation: toolbar, filters, sort, dense rows, loading/error/empty, address/tag treatment.
3. Accessibility and responsive verification: focus/state semantics, reduced motion, 375/390/430/1280/1440 checks, screenshots.

These are implementation steps, not separate approvals or new architecture. No functional behavior should be changed between passes.

## 23. Regression risks

| Risk | Mitigation |
|---|---|
| Markup styling accidentally changes checkbox/radio behavior | Keep native inputs and existing handlers; test keyboard and mouse paths. |
| Mobile filter strip creates page overflow | Constrain overflow to the filter container and test 375px. |
| A compact layout hides the resolved location or confirmation action | Keep matched name/address first and retain an explicit 修改 action. |
| Cost/rating null values gain unwanted placeholder text | Preserve existing formatter output and omission rules. |
| Sort/filter/load-more behavior changes during markup edits | Do not touch `src/web/logic.ts`; rerun all 26 tests and browser regression. |
| Error/empty state becomes color-only | Keep text labels and semantic live/alert attributes. |
| Excessive CSS polish expands scope | Limit files and tokens; no new library, animation system, or design system. |

- initial page with compact header and controls;
- resolved location with category/radius controls;
- all-category result list and toolbar;
- single-category result list with cost sort;

Mobile 375/390/430:

## 25. Functional acceptance criteria

All B-2A behavior must remain unchanged:

- existing 26 automated tests pass;
- `npm run check` and `npm run build` pass;
- category toggle, group toggle, all/clear, zero-selection guard, and radius values remain correct;
- category/radius/query stale invalidation remains correct;
- filters, All merge, exact id dedupe, sort scope/fallback, and local load more remain local-only;
- no filter, sort, or load-more action creates `/api/search` traffic;
- formatter output never shows `null`, `undefined`, or `NaN`;
- partial success continues to preserve successful categories;
- Shenzhen and Hong Kong browser regressions pass for the established B-2A flow;
- screenshots meet the desktop/mobile checklist at all required widths;
- no AMap/search core, API contract, or server Key boundary changes appear in the diff.

## 26. Out of scope

- Any new search capability or provider.
- AMap client, search service, API contract, category strategy, radius values, dedupe, or load-more algorithm changes.
- Favorites, notes, visited/want-to-go/exclude, database, login, sessions, analytics.
- Maps, navigation, route planning, POI detail pages, hotel real-time prices, OTA, Meituan, scraping.
- Custom categories, search templates, natural-language search, AI recommendations, streaming, API page 2+.
- Tailwind, MUI, Ant Design, Chakra, shadcn, Bootstrap, accessibility libraries, virtual lists, Redux, Zustand, Context, or a new design system.
- Large-scale visual redesign, marketing hero, dashboard/sidebar layout, gradients, glassmorphism, or decorative animation.

## Split decision

Do not split B-2B into multiple approvals. The scope is limited to `SearchApp.tsx` markup and `globals.css`; one IMPLEMENT phase with the three internal passes above is easier to verify and avoids process overhead. If implementation reveals that a functional change is required, stop and request a new plan instead of widening B-2B.
