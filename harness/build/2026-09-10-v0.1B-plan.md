# v0.1B Web App Plan

Status: `AWAITING_PLAN_APPROVAL`

This document is a plan only. It does not authorize implementation. v0.1A is accepted as the data/search core; v0.1B must be approved again before any Next.js, React, UI, or API files are created.

## 1. Scope and outcome

Build the first usable single-page web tool for searching nearby services around a user-confirmed location on desktop and mobile.

The user flow is deliberately two-stage because a bare `香港城市大学` query previously resolved to Chengdu:

```text
query -> resolve location -> show resolved location -> user confirms
      -> search selected categories around confirmed center -> local filter/sort/reveal
```

The first page has no map, accounts, persistence, favorites, hotel prices, AI, second provider, or product dashboard.

### In scope

- Next.js App Router integration into the existing package.
- Server-only AMap access through two Route Handlers.
- Location resolution and explicit confirmation.
- Eight preset categories and four radius choices.
- Serial AMap search with the existing 500ms interval and category-level error isolation.
- Partial success, empty, error, loading, and invalid-request states.
- Local category filtering, rating/distance/cost sorting, and in-memory 10 -> 20 -> 25 reveal.
- Responsive plain CSS, keyboard access, focus-visible states, and compact list-first result rows.
- Automated core/API tests, Next build, and manual Shenzhen/Hong Kong browser smoke checks.

### Out of scope

- Database, Prisma, login, accounts, favorites, notes, saved searches, custom categories, templates.
- HotelOfferProvider, hotel pricing, check-in/check-out, OTA, Meituan, scraping.
- Map SDK, navigation, route planning, second POI provider.
- AI, natural-language search, recommendations, analytics.
- API page 2+, SSE, streaming, Redis, complex cache, virtual-list library.
- Any rewrite of the already verified `src/amap/*` and `src/search/*` core beyond a small resolved-center seam.

## 3. Current repository and build boundary

Current package is a Node.js + TypeScript CLI:

- `src/amap/*`: AMap client, category configuration, distance, Smoke validation.
- `src/search/*`: request contracts, validation, serial search service, pure sorting.
- `scripts/amap-smoke-test.ts`: real API Smoke.
- `test/*`: 17 core tests.
- `tsconfig.json`: current `tsc` project, `rootDir: .`, `outDir: dist`, strict NodeNext compilation.
- `npm run build`: currently runs `tsc`, producing `dist/src`, `dist/scripts`, and `dist/test`.
- `npm run check`: current project type-check with `tsc --noEmit`.
- `npm test`: current build followed by Node test runner over compiled tests.
- `npm run smoke`: current build followed by the CLI Smoke script.

### Minimal Next.js integration

Do not rewrite the core into an app directory. Add Next.js beside it:

```text
app/                         Next.js route and page entrypoints
src/web/                     client components and UI-only formatting
src/server/                  server-only AMap boundary and route helpers
src/amap/, src/search/       existing reusable core
scripts/, test/              existing CLI and core tests
dist/                        core TypeScript output only
.next/                       Next.js output only
```

Use one package and two TypeScript projects:

- `tsconfig.core.json`: preserves the current NodeNext, strict, emitting core build to `dist`; includes `src/**/*.ts` excluding web-only files, `scripts/**/*.ts`, and `test/**/*.ts`.
- `tsconfig.json`: becomes the Next project config with `jsx: preserve`, `noEmit: true`, Next plugin/types, `app/**/*.ts(x)`, `src/**/*.ts(x)`, `next-env.d.ts`, and `.next/types/**/*.ts`. It must exclude `dist`, `node_modules`, and core test output paths.

This split prevents Next JSX and `.next` generated types from entering the Node CLI compiler. It also keeps `dist` and `.next` independent. The exact Next-generated `tsconfig` plugin lines may be accepted, but the core config must remain explicit and stable.

## 4. Server API contracts

### POST `/api/resolve-location`

Request:

```ts
{ query: string }
```

Validation:

- JSON object only.
- No unknown fields.
- Trimmed query length 1-200.
- No AMap key, arbitrary types, keyword, radius, or page controls.

Success response:

```ts
{ resolvedLocation: GeocodedPlace }
```

The route calls the existing server-side `client.geocode(query)` once. It returns the formatted address, province, city, district, level, longitude, and latitude so the browser can show exactly what will be searched. A geocode no-result or AMap error becomes a sanitized structured error; the raw key and request URL never enter the response.

### POST `/api/search`

The route must not geocode again. The browser sends the confirmed resolved snapshot and center:

```ts
{
  center: { longitude: number; latitude: number },
  resolvedLocation: GeocodedPlace,
  categoryIds: CategoryKey[],
  radiusMeters: 1000 | 2000 | 3000 | 5000
}
```

`resolvedLocation` is a confirmed display snapshot. The server validates its shape and requires its coordinates to equal `center`; search execution uses only the validated center coordinates. No user-supplied query is re-geocoded. This keeps the existing `SearchResponse.resolvedLocation` contract without inventing a signing or repository layer. Display strings are not treated as security-sensitive authority.

Validation rejects:

- empty/unknown/duplicate category ids;
- invalid longitude outside -180..180;
- invalid latitude outside -90..90;
- non-finite numbers;
- unsupported radius;
- unknown fields, arbitrary keyword/types, API key, pageSize, pageNumber, or custom category data.

Success response reuses the existing shape:

```ts
{
  resolvedLocation: GeocodedPlace,
  categories: CategorySearchResult[],
  status: "success" | "partial success"
}
```

Each category remains `success`, `empty`, or `error`. Category errors retain sanitized `message`, `info`, and `infocode`. The response is still useful when one category fails. A request with all category calls failing is rendered as an error/empty result state while preserving each category error; no error response reveals a key, URL, stack, or raw server exception.

### Minimal core refactor

Add a resolved-center entry point, not a new hierarchy:

```ts
executeResolvedSearch(request: {
  center: Coordinates;
  categoryIds: CategoryKey[];
  radiusMeters: SearchRadius;
}, client): Promise<CategorySearchResult[]>
```

The existing CLI-oriented `executeSearch(query, ...)` may remain as a small wrapper that geocodes then delegates. The Route Handler uses the resolved-center entry point. Keep `searchCategoriesSequentially` as the single serial/QPS implementation. Do not create repositories, providers, schedulers, or duplicate category search functions.

## 5. API key boundary

Create one small server-only module, for example `src/server/amap.ts`:

```ts
export function createServerAmapClient() {
  const key = process.env.AMAP_WEB_SERVICE_KEY;
  if (!key?.trim()) throw new MissingServerKeyError();
  return createAmapClient(key);
}
```

Only `app/api/*/route.ts` imports this module. Never use `NEXT_PUBLIC_AMAP_WEB_SERVICE_KEY`; never import this module from a client component; never put the key in request/response JSON, logs sent to the browser, or thrown error text. Route errors are mapped to safe public messages while development-only server logs may retain AMap `info`/`infocode` without the key or full URL.

Security tests use a sentinel fake key and mocked fetch:

- resolve success body does not contain the sentinel;
- search success body does not contain the sentinel;
- validation and upstream error bodies do not contain the sentinel;
- client component source/bundle-facing props do not accept a key;
- arbitrary `keywords`, `types`, `pageSize`, and `pageNumber` are rejected.

## 6. Page/component model

Keep one page, not a dashboard:

```text
app/layout.tsx
  app/page.tsx
    SearchApp (client boundary)
      SearchForm
        LocationInput
        CategorySelector
        RadiusSelector
        ResolveButton / SearchNearbyButton
      ResolvedLocation
        LocationConfirmation
      SearchStatusSummary
      ResultsToolbar
        CategoryFilterTabs
        SortSelect
      ResultsList
        PlaceRow
      CategoryErrorSummary / EmptyState
```

`app/page.tsx` can be a thin server-rendered shell. `SearchApp` owns interactive state. `PlaceRow` is a compact list row, not a large card. The page max width is about 960-1080px, with one restrained accent color, system fonts, CSS variables, subtle borders, small radius, and little shadow. No map or hero/dashboard region.

### React state

```ts
type Phase = "idle" | "resolving" | "awaiting-confirmation" | "searching" | "success" | "partial" | "error";

query: string;
resolvedLocation: GeocodedPlace | null;
confirmedLocation: GeocodedPlace | null;
selectedCategoryIds: Set<CategoryKey>;
radiusMeters: SearchRadius;
phase: Phase;
response: SearchResponse | null;
activeFilter: "all" | CategoryKey;
sortMode: SortMode;
visibleCountByScope: Record<string, number>;
publicError: string | null;
```

Initialize all eight categories and 3000m. Use `useMemo` for visible filtered/sorted results and derived group checkbox state. A `requestGeneration` ref or equivalent ignores stale resolve/search responses when a user edits quickly; no complex state library is needed.

### Location invalidation

- Editing `query` immediately invalidates `resolvedLocation`, `confirmedLocation`, the prior response, and active result state when the value differs from the resolved query.
- “修改地点” clears the confirmed location and old results and returns to the input state.
- Only a successful resolve enters `awaiting-confirmation`.
- Only the explicit confirmation action enables `/api/search`.
- Search button is disabled until a confirmed location exists and at least one category is selected.

This prevents query A from accidentally searching the coordinates resolved for query B.

### Category and radius controls

The client stores ids only. It imports labels/groups from a safe shared configuration or a server-provided allowlisted view, never typecodes. Group checkbox state is derived from selected ids. Support individual toggle, group toggle, select all, and clear all. Clearing all disables search and shows a text explanation.

Radius is a four-value allowlist: 1000, 2000, 3000, 5000. Default is 3000. Use real labels 1 km, 2 km, 3 km, 5 km.

### Filtering and sorting

Category tabs are derived from the selected ids and do local filtering only. “全部” merges successful category places; it never refetches. `all` and mixed results expose only distance/rating sort. A single category exposes the cost modes allowed by `priceMode`. Call the existing `sortPlaces` and `isSortModeAllowed`; do not duplicate comparator code in React.

Null rating/cost remain last. Sorting and filtering operate on the loaded in-memory arrays and preserve source arrays.

### Reveal / load more

The API still fetches only page 1/page size 25 per category. The browser owns `visibleCountByScope`:

- new search resets every scope to 10;
- a single category reveals 10 -> 20 -> 25;
- “全部” reveals 10 -> 20 -> 30 and then +10 until its loaded result count, at most 200;
- switching filter keeps an independent scope count, reset to 10 on a new search;
- sorting changes order only and does not reset loaded data;
- hide load-more when visible count reaches the current loaded count.

This is UI reveal state, not API pagination. Do not create `src/search/pagination.ts` or a page-2 client in v0.1B.

### Partial success and errors

After search, show a compact summary such as “7 个类别成功，1 个类别失败”. Successful results remain visible. Empty categories show an empty message. A failed category shows its label and safe public error; other categories are not replaced by a global failure. Geocode failure blocks search until the user edits or retries resolve. Missing server key, invalid request, network failure, no geocode result, all-category failure, and partial success each get a distinct public state.

### Result formatting

- `< 1000m`: `620 m`; `>= 1000m`: `1.6 km`.
- Rating: `★ 4.6`; missing rating is omitted, never `null` or “暂无评分”.
- Hotel and mall cost are omitted.
- Hotpot/bakery use `人均`; dessert may use `人均` or `参考消费`, fixed consistently in the formatter.
- KTV uses `参考消费`.
- Gym uses weak `参考消费` when present and never participates in cost sort.
- Billiards cost is omitted in v0.1.
- Tag is split on AMap comma-separated values and displays at most three items joined by ` · `.
- Address and English POI names remain intact.

## 7. Responsive and accessibility plan

Plain CSS with variables and a small breakpoint:

- desktop: search controls can share a row, results remain list-first;
- mobile: location input full width, category panel collapsible, large enough radius controls, single-column rows, non-overflowing sort control;
- no hover-only actions.

Use real `label`, `button`, and checkbox elements. Add `:focus-visible`, keyboard toggling for groups/categories, `aria-busy` on the search region, an `aria-live` status for resolve/search progress, and text errors that are not communicated by color alone. Do not add an accessibility framework.

## 10. Failure and risk registry

| Risk | User-visible failure | Mitigation / gate |
|---|---|---|
| Next changes the existing tsconfig | core CLI/tests stop compiling | separate `tsconfig.core.json`, run core checks independently |
| Route imports server key into client bundle | credential exposure | server-only module, no `NEXT_PUBLIC`, sentinel bundle/response tests |
| Search runs before confirmation | wrong center searched | client phase guard plus route requires confirmed center snapshot |
| Stale resolve response wins | query A shows location B | request generation guard and query invalidation |
| One category fails | all results disappear | per-category status and partial response |
| AMap count is mistaken for page count | misleading load-more | reveal only loaded `places`, keep `mayHaveNextApiPage` informational |
| All results render 200 rows | mobile and desktop become unwieldy | 10-item initial reveal and +10 local reveal |
| cost semantics look authoritative | misleading price expectations | category-specific labels, omission/weak display, no hotel price |
| long tags break rows | dense layout becomes unreadable | three-item tag truncation |
| Hong Kong/English names are hidden by keyword | recall loss | final types-only strategies and manual Hong Kong smoke |
