# 地点周边生活服务聚合器 v0.1 产品化实施计划

## 1. 决策摘要

本轮工作应拆成两个独立验收阶段：

- **v0.1A 搜索核心产品化**：类别/typecode、AMap 原生 distance 兼容、分页契约、排序、请求校验、服务编排与测试。继续保持无 UI，可单独用 Smoke 验证。
- **v0.1B Web 产品界面**：在 v0.1A 已验证契约上引入 Next.js/React、服务端 API Route、响应式页面、类别与半径控件、结果列表、加载更多、排序和状态展示。

本计划的当前审批门只覆盖 **v0.1A**。v0.1B 即使写在同一计划中，也必须在 v0.1A 验收后再次获得明确批准。

拆分理由：数据精度、distance 选择和分页/排序契约会决定 UI 数据形状。先验证这些内容，可以让 v0.1B 只处理服务端边界与交互，避免在同一轮同时调试 AMap 召回、领域逻辑、Next.js 配置和浏览器状态。

## 2. 当前架构

当前仓库是单包 Node.js + TypeScript CLI：

```text
scripts/amap-smoke-test.ts
        |
        +--> src/amap/smoke.ts
        |      - 香港 Smoke 校验
        |      - 8 类串行请求
        |      - 相邻 Around 请求间隔 500ms
        |
        +--> src/amap/client.ts
               - v3 geocode
               - v5 place/around
               - AMap 错误解析
               - POI 标准化
               |
               +--> categories.ts
               +--> distance.ts
               +--> types.ts
```

已验证基线：

- 8/8 Node 单元测试通过。
- TypeScript 检查通过。
- 深圳北站真实 geocode：广东省 / 深圳市 / 龙华区，`114.025796,22.608443`。
- 香港结构化地址真实 geocode：香港特别行政区 / 深水埗区，`114.176938,22.334752`。
- 两地 8 类真实 Around 搜索均成功。
- 串行 + 500ms 间隔后真实复测不再出现 QPS 错误。
- 一个类别失败不会中断后续类别。

当前限制：

- `CATEGORIES` 只有 keyword，误召回明显。
- `Place.distanceMeters` 只使用 Haversine，尚未读取官方响应中的 `distance`。
- `searchNearby` 固定 page 1/page size 25，返回裸数组，没有分页元数据。
- 排序和展示上限仍属于 CLI 逻辑，没有产品级纯函数与请求契约。
- 尚无 Web/API 安全边界。

## 3. 直接复用的 Spike 代码

以下能力不重写：

- `src/amap/client.ts` 的 `createAmapClient`、原生 `fetch`、v3/v5 endpoint、响应容错和 `AmapApiError`。
- `src/amap/distance.ts` 的 Haversine 实现，继续作为 fallback 与对比基准。
- `src/amap/smoke.ts` 的 500ms 可注入 delay、串行执行、失败隔离。
- `src/amap/types.ts` 的坐标、geocode 和基础 Place 字段。
- `scripts/amap-smoke-test.ts` 的两地真实验证入口。
- 现有 8 个测试全部保留并随契约调整。

不复制第二套 AMap client，不增加第二 Provider。

## 4. 为什么现在值得引入 Next.js

**结论：值得，但放在 v0.1B，不放进 v0.1A。**

Next.js App Router 适合这个小产品，原因是：

- 一个仓库同时承载 React 页面和服务端 Route Handler，避免单独搭建 Express/BFF。
- `AMAP_WEB_SERVICE_KEY` 可只由服务端 Route Handler 读取，不需要交给浏览器。
- 页面只有一个主工作流，不需要全局状态框架或复杂路由。
- 当前 Node 24 环境满足 Next.js 运行要求。

计划使用实施时的最新补丁级 Active LTS；截至 2026-09-10，官方列出的 Active LTS 是 **Next.js 16.3.3**。不使用 RC、canary 或实验功能。

安全边界：

- 浏览器只调用项目自身的 `POST /api/search`。
- `AMAP_WEB_SERVICE_KEY` 不加 `NEXT_PUBLIC_` 前缀，不写入 `next.config` 的 `env`，不作为函数参数从客户端传入。
- 新增一个极薄的 `src/server/amap.ts`，用 `server-only` 标记并在服务器读取环境变量，再创建现有 AMap client。
- Route Handler 只返回标准化业务数据和必要错误，不返回请求 URL、headers 或 Key。

官方依据：

- Route Handler 位于 App Router 的 `app` 目录并使用 Web Request/Response API：https://nextjs.org/docs/app/getting-started/route-handlers
- 非 `NEXT_PUBLIC_` 环境变量默认只在服务端可用：https://nextjs.org/docs/app/guides/data-security
- Next.js 16.3.3 Active LTS：https://nextjs.org/blog

CSS 选择：**普通 CSS + CSS variables，不引入 Tailwind**。页面只有一个主界面，Tailwind 的依赖和配置收益不足。也不引入组件库。

## 5. v0.1A：搜索核心产品化

### 5.1 目标

在不引入 UI 的前提下，把已验证 Spike 变成稳定、可供 API/UI 直接消费的搜索核心，并用深圳与香港 Smoke 数据验证精度和距离策略。

### 5.2 类别配置模型

将 `CategoryConfig` 扩展为配置驱动的 `SearchCategory`：

```ts
type CategoryGroup = "stay" | "shopping" | "food" | "entertainment";

type PriceMode =
  | "none"
  | "per-person-sortable"
  | "reference-sortable"
  | "reference-display-only";

interface SearchCategory {
  id: CategoryKey;
  label: string;
  group: CategoryGroup;
  keyword: string | null;
  types: readonly string[];
  priceMode: PriceMode;
}
```

`entertainment` 只用于 UI 分组，永远不传给 AMap。

价格策略：

| 类别 | group | priceMode | UI 含义 |
|---|---|---|---|
| 酒店 | stay | none | 不使用、不展示 AMap cost |
| 商场 | shopping | none | 不展示消费字段 |
| 火锅 | food | per-person-sortable | 人均，可排序 |
| 面包 | food | per-person-sortable | 人均，可排序 |
| 甜品 | food | per-person-sortable | 人均，可排序 |
| KTV | entertainment | reference-sortable | 参考消费，可排序 |
| 台球厅 | entertainment | none | v0.1 不显示/排序 cost |
| 健身房 | entertainment | reference-display-only | 弱化显示参考消费，不参与排序 |

### 5.3 typecode 精度策略

优先采用 **精确 types-only**，而不是 `name.includes`。原因：官方说明 `sortrule=distance` 在只传 keywords 时不生效，精确 typecode 同时解决误召回与服务端距离排序条件。

候选配置来自高德官方 `Amap_poicode.zip`（V1.06，2023-02-08）：

| 类别 | AMap types | 官方分类 |
|---|---:|---|
| 酒店 | 100100 | Accommodation Service / Hotel |
| 商场 | 060100 | Shopping / Shopping Plaza |
| 火锅 | 050117 | Food & Beverages / Chinese Food / Hotpot Restaurant |
| 面包 | 050800 | Food & Beverages / Bakery |
| 甜品 | 050900 | Food & Beverages / Dessert House |
| KTV | 080302 | Sports & Recreation / Recreation Center / KTV |
| 台球厅 | 080113 | Sports & Recreation / Sports Stadium / Pool Room |
| 健身房 | 080111 | Sports & Recreation / Sports Stadium / Gym Center |

上述 `types-only` 是首轮候选，不是预设最终答案。当前 keyword-only 真实结果保留为 baseline；每个类别独立比较 baseline 与 candidate 后，最终策略允许分别选择 `types-only`、`keyword-and-types` 或必要时 `keyword-only`，不为形式统一牺牲召回质量。

所有数字 typecode 只能存在于 `src/amap/categories.ts` 的 category configuration。client、service、Smoke 和测试只读取配置，不重复硬编码这些数字。

Smoke 验证门：

- 深圳与香港每类 baseline/candidate 记录总数、前 10 名名称/type/typecode，以及实际 requested types。
- 重点确认已知三个误召回是否消失。
- 若 types-only 导致某类两地均明显召回不足，才在该类别配置中补一个 AMap 支持的单 keyword；不建立规则引擎，不做 name 后过滤。

官方依据：

- Around 支持 `types`、page size 1-25，并说明 keywords-only 时 `sortrule=distance` 不生效：https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch
- 官方分类码下载：https://a.amap.com/lbs/static/code_resource/Amap_poicode.zip

### 5.4 原生 distance 与 computed fallback

扩展标准模型：

```ts
interface Place {
  // 现有字段保持
  distanceMeters: number;
  distanceSource: "amap" | "computed";
  amapDistanceMeters: number | null;
  computedDistanceMeters: number;
}
```

归一化规则：

1. 始终从中心点和 POI location 计算 `computedDistanceMeters`。
2. 将 AMap 原生 `distance` 解析为有限且不小于 0 的数；缺失、数组、空串、NaN 或负数视为不可用。
3. 原生值有效时：`distanceMeters = amapDistanceMeters`，`distanceSource = "amap"`。
4. 原生值无效时：`distanceMeters = computedDistanceMeters`，`distanceSource = "computed"`。
5. 不根据任意误差阈值自动否定原生值；Smoke 只记录差异，避免在无证据时增加复杂规则。

Smoke 输出同时显示：

- `amapDistanceMeters`
- `computedDistanceMeters`
- `distanceSource`
- 两者绝对差值（原生存在时）

验收时汇总深圳与香港各类别原生 distance 覆盖率及最大/中位差值。如果原生字段稳定存在且差异合理，v0.1 产品字段采用上述“原生优先、computed fallback”策略；Haversine 永久保留为 fallback。

官方 Around 返回模型已明确列出 `distance`，单位米：https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch

### 5.5 分页契约

v0.1 选择 **方案 A：每类别只请求 API page 1、page_size=25，UI 本地逐步展示**。

理由：8 类串行请求已经需要约 3.5 秒固定间隔。v0.1 自动请求 page 2 会明显增加等待、QPS 和错误组合，而大多数快速比较场景不需要每类超过 25 条。

但底层不写死 page 1：

```ts
interface NearbySearchOptions {
  radiusMeters: 1000 | 2000 | 3000 | 5000;
  pageNumber: number;
  pageSize: number;
}

interface PlacePage {
  places: Place[];
  pageNumber: number;
  pageSize: number;
  returnedCount: number;
  mayHaveNextApiPage: boolean;
}
```

- `searchNearby` 接受 pageNumber/pageSize，限制 pageSize 1-25、pageNumber >= 1。
- v0.1 产品服务只调用 page 1/25。
- `mayHaveNextApiPage = places.length === pageSize` 只是可继续请求的提示，不宣称 AMap 返回了总数。
- `10 → 20 → 25` 属于 v0.1B React 本地状态，不在 v0.1A 创建 pagination/reveal abstraction。
- 真正 page 2+ 延后；将来可以沿用现有 options/PlacePage，无需改 Place 或 API 基本形状。

### 5.6 排序契约

新增无副作用纯函数 `sortPlaces(places, sortMode)`，不修改输入数组。

排序模式：

- `distance-asc`：所有结果和所有类别可用。
- `rating-desc`：所有结果和所有类别可用，null 永远最后。
- `cost-asc` / `cost-desc`：只对 priceMode 为 `per-person-sortable` 或 `reference-sortable` 的单一类别开放，null 永远最后。

稳定 tie-break：

1. 主排序字段。
2. `distanceMeters` 升序。
3. `name`。
4. `id`。

禁止跨业态 cost 排序。健身房、台球厅、酒店、商场不开放 cost sort。

### 5.7 产品搜索请求/响应契约

新增纯 TypeScript 合约：

```ts
interface SearchRequest {
  query: string;
  categoryIds: CategoryKey[];
  radiusMeters: 1000 | 2000 | 3000 | 5000;
}

interface SearchResponse {
  resolvedLocation: GeocodedPlace;
  categories: CategorySearchResult[];
}
```

请求校验：

- query trim 后 1-200 字符。
- categoryIds 必须非空、去重且全部属于 8 个预设 id。
- radius 只能是 1000/2000/3000/5000。
- 浏览器不得提交 keyword/types、Key、pageSize 或任意自定义类别。

产品服务：

1. geocode query。
2. 返回完整 `resolvedLocation`，不假设输入等于唯一正确位置。
3. 按用户选择顺序串行搜索类别，沿用 500ms 间隔和失败隔离。
4. 每类别返回 success/empty/error，错误保留 message/info/infocode。
5. 不把在线 API 调用放入普通单元测试。

## 6. v0.1B：Next.js Web 产品界面

### 6.1 最小架构

```text
Browser
  |
  +--> app/page.tsx
  |      +--> SearchExperience client component
  |             - query/category/radius controls
  |             - local sort/filter/reveal state
  |             - result and error states
  |
  +--> POST /api/search
         +--> request validation
         +--> src/server/amap.ts (server-only env boundary)
         +--> src/search/service.ts
                  +--> existing src/amap/*
```

不增加 Redux、React Query、Zustand、ORM、数据库或组件库。一次搜索只有一个请求，组件内 `useState` 足够。

### 6.2 API Route

`POST /api/search`：

- 接受 v0.1A `SearchRequest`。
- 读取服务端 `AMAP_WEB_SERVICE_KEY`。
- 调用现有 AMap client 与产品 search service。
- 返回 resolved location、每类别结果和结构化错误。
- 请求非法返回 400；缺 Key 返回 500 安全错误；上游 geocode/API 故障返回合适 502；部分类别失败仍返回 200 和 partial results。
- `Cache-Control: no-store`，不持久化真实响应。
- 不提供让浏览器指定 endpoint、types、keyword 或 page size 的能力。

### 6.3 地点解析最小 UX

v0.1 不做 autocomplete 或候选选择器。

搜索完成后，在结果列表前持续显示：

```text
已定位为：香港特别行政区深水埗区九龙达之路城市大学
深水埗区 · 114.176938, 22.334752
```

旁边提供“修改地点”动作，将焦点送回输入框。结果不会把用户原始输入当作已确认标准地址。

现有香港 Smoke 校验继续留在 Smoke，不扩展成通用行政区推断器。**v0.1B 审批前必须重新评估产品正确性流程**：是采用 `query → geocode → 显示 resolved location → 用户确认 → Around`，还是自动执行 Around 后再显示匹配结果。裸输入“香港城市大学”曾落到四川成都，因此不能在 v0.1B 未评审该选择时默认后者。完整候选地点选择仍延后。

### 6.4 页面结构

单页、list-first，无 sidebar、地图和统计卡：

```text
页面标题 / 一句用途说明

[ 地点输入........................ ] [类别] [搜索]
[1 km] [2 km] [3 km] [5 km]

类别展开面板
  全选  清空
  住宿：酒店
  购物：商场
  餐饮：火锅 / 面包 / 甜品
  娱乐：KTV / 台球厅 / 健身房

已定位为：实际 formatted address

[全部] [酒店] [商场] [火锅] ...    [排序]
结果/错误摘要

POI list
加载更多
```

桌面：输入、类别、搜索同一行，内容最大宽度约 960-1080px。

手机：输入占满首行，类别和搜索在下一行；类别面板成为页面内折叠区，不引入复杂浮层；结果卡保持单列。

### 6.5 视觉方向

- 普通系统字体，先保证中英文与数字可读性，不下载 Web Font。
- 浅色页面，近白背景、深灰正文、一个克制的蓝绿色交互色。
- 8px 基础间距，少量 8-12px 圆角。
- 只给搜索容器、类别面板、结果项必要的层次；不把每个标签都做成厚重 card。
- 边框比阴影优先，动画只用于 150-200ms 的展开/状态变化。
- 明确 `:focus-visible`、键盘操作、按钮 disabled 和错误色对比。
- 不做渐变、玻璃拟态、巨型 hero、dashboard sidebar 或装饰性统计。

### 6.6 UI 状态

v0.1B 选择 **整体等待，不做服务端 progressive streaming**。

原因：8 类串行搜索约有 3.5 秒固定间隔；真正逐类流式返回会引入 SSE/ReadableStream、客户端增量合并和断线语义，超过 v0.1 收益。

状态模型：

- initial：搜索控件 + 简短示例，无空白错误卡。
- searching：锁定当前提交按钮，保留输入可见，显示“正在依次搜索 N 个类别”；选中类别标记 pending。
- geocode failure：顶部明确错误，不显示旧结果为新结果。
- success：先显示“已定位为”，再显示结果。
- category success：有结果列表。
- category empty：显示“3km 内未找到该类别”。
- category error：显示该类别错误摘要，不吞掉其他类别结果。
- partial success：顶部提示“部分分类搜索失败”，成功项正常可用。
- all complete：解除提交锁定，显示总结果数和失败类别数。

不支持并行或流式 Around；服务端继续使用现有串行策略。

### 6.7 结果、加载更多与排序 UI

- API 每类别预取最多 25 条。
- 结果视图有“全部”及每个已选类别过滤项。
- “全部”视图把已加载 Place 合并，只提供距离和评分排序；本地每次多显示 10 条。
- 单类别视图本地显示 10 → 20 → 25；达到 25 后隐藏“加载更多”。
- 切换排序只处理内存中的 Place[]，不请求 AMap。
- 单类别可用排序项完全来自 `priceMode`，前端不复制类别规则。

结果卡：

- 名称、类别、距离、rating、合理 cost、tag、地址。

- rating 缺失显示“暂无评分”，不显示假星级。
- 餐饮 cost：`人均 ¥108`。
- KTV cost：`参考消费 ¥74`。
- 健身房 cost：次要行显示 `参考消费 ¥...` 或 `参考消费暂无`，不参与排序。
- 酒店和商场不显示 AMap cost。
- 台球厅 v0.1 不显示 cost。
- 酒店不展示假房价，也不放置无法工作的“查看房价”按钮；Hotel Price Spike 完成后再加入真实 CTA。

## 8. 风险与控制

| 风险 | 控制 |
|---|---|
| types-only 提升精度但降低召回 | v0.1A 两地逐类 Smoke 对比，按类别单独决定是否补 keyword |
| AMap distance 与 Haversine 差异 | 同时保留并输出两值，原生仅在有效时优先，computed 永远可 fallback |
| 8 类串行导致页面等待较长 | v0.1B 明确整体 searching 状态；不以并发换速度，不引入 streaming |
| 一个类别失败拖垮整次搜索 | 复用已测试的类别级错误隔离，API 返回 partial success |
| Key 泄露浏览器 | server-only env accessor、无 NEXT_PUBLIC、Route 响应泄露测试 |
| AMap count 被误当总数 | 命名 returnedCount，只把满 25 条视为“可能还有下一页” |
| cost 语义跨业态错误 | priceMode 单一事实源；全量视图禁止 cost sort |
| 地点误匹配 | UI 显著展示 resolvedLocation；autocomplete/candidate picker 延后 |
