## 1. Scope and request discipline

This artifact covers only the isolated resolver Spike. It does not change production `/api/resolve-location`, SearchApp, Nearby Search, pagination, deployment, DNS, or any v0.2 implementation.

The original A–D comparison was not rerun. A new `resolver:address-micro` command was added for E1/E2 only. Requests are serial and separated by approximately 500 ms; no retry or concurrent scheduler is used. Output is redacted structured data only: no key, Authorization header, complete secret-bearing URL, or raw payload dump.

## 2. Provider-returned evidence (real review)

The following findings are provider-returned observations from the completed real Spike review. They are not inferred from the local experiment:

### 深圳北站

- Geocode baseline: `深圳北站(公交站)`.
- POI candidate rank 1: `深圳北站`, type `火车站`, typecode `150200`.
- Metro station, bus stop, entrance, and related entities were visible as additional candidates.
- Candidate search was materially better than taking the first geocode result.

### 香港城市大学

- Geocode baseline returned the known wrong Chengdu/Sichuan entity.
- POI candidate search returned Hong Kong SAR City University-related entities.
- The provider did not guarantee one canonical university entity, so the first candidate must not be silently confirmed.

### 澜庭酒店 深圳罗湖

- Geocode baseline resolved to Shenzhen Luohu district and lost the hotel subject.
- Full raw-query POI search rank 1: `澜庭酒店(深圳东门晒布地铁站店)`, Shenzhen, Luohu.
- Preserving the complete raw query is therefore supported; decomposition is not required as a first step.

### 维也纳酒店

- Geocode failed.
- POI candidate search returned multiple valid hotel branches across regions.
- Ambiguous queries require candidate confirmation; the first item is not safe to auto-confirm.

## 5. Decision answers

1. For place-name/entity-like queries, POI candidate search is better supported than first-result geocoding by A–D.
2. For pure street/doorplate addresses, geocode returned the exact address entity in both E1 and E2; POI search returned nearby entities located at those addresses rather than a cleaner canonical address result.
3. Evidence supports `place-name → POI candidates` and `structured street address → geocode fallback` without an LLM or second provider.
4. The default router can conservatively choose between those two paths using strong street/doorplate evidence, while retaining the complete raw query.

## 6. Architecture implications (Spike only)

- POI candidate search should replace first-result geocode as the preferred path for place-name queries once separately approved for implementation.
- Geocode should remain the primary path for strong structured street/doorplate addresses.
- Place type is useful evidence for user-facing confirmation but is not canonical: AMap type/typecode can be wrong.
- Region evidence is strong enough to reject obvious conflicts (for example Hong Kong versus Chengdu), but not sufficient to auto-select among same-name branches.
- Main-place versus subordinate-place distinction is partially supported by visible type/typecode and related candidates, but still requires confirmation.
- Multi-clue intent can be preserved without an LLM by retaining the complete raw query and applying conservative deterministic evidence checks; no parser is required as the first step.
- The evidence does not require an LLM or second provider for the next design step.
