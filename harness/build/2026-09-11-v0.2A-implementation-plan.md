# v0.2A Location Intent Resolution Implementation Plan

Status: `V0.2A_PRODUCTION_VERIFICATION_BLOCKED`

This is a PLAN only. It does not authorize implementation, new provider calls, deployment changes, or v0.2B pagination.

## 1. Scope and acceptance gate

Implement only location intent resolution for the existing two-stage flow. The accepted outcome of the real Spike is:

- place-name / POI-like query → AMap POI candidate search;
- pure street / doorplate address → AMap geocode;
- ambiguous or conflicting evidence → `needs_confirmation`, never silent first-result confirmation.

Acceptance requires deterministic unit coverage, existing tests/builds passing, and browser verification for the eight resolver cases listed in Section 14. No implementation starts until this plan is separately approved.

## 3. Query Intent Router

`routeQuery(rawQuery)` is a pure, conservative function returning `PLACE_QUERY` or `ADDRESS_QUERY` plus non-authoritative clue metadata. It always retains the trimmed original `rawQuery`.

Address classification requires strong street/doorplate evidence such as a street/road term plus a number or an explicit door/building marker. Province/city/district words alone never make an address. A query containing a clear named POI, such as `广东省深圳市龙华区深圳北站`, remains `PLACE_QUERY`.

Ambiguous input defaults to `PLACE_QUERY`, because candidate confirmation is safer than silently accepting a geocode first result. No NLP framework, LLM, translation service, large address ontology, blacklist, or query-specific exception is permitted.

## 4. LocationCandidate contract

```ts
interface LocationCandidate {
  id: string;
  name: string;
  placeType: string | null;
  typeCode: string | null;
  province: string | null;
  city: string | null;
  district: string | null;
  address: string | null;
  longitude: number;
  latitude: number;
  source: "poi" | "geocode";
  providerRank: number;
}
```

Provider-missing optional fields are `null`; malformed coordinates or missing required identity are discarded. The browser depends only on this normalized shape, never AMap field names. `providerRank` is diagnostic ordering, not a confidence score.

## 5. Resolver service boundary

`resolveLocation(rawQuery, dependencies)` owns routing, provider calls, normalization, and evidence state. The dependency surface is small:

- `geocode(query)` from the existing client;
- `searchPlaceCandidates(query)` from the new POI text adapter.

The service returns `{ query, intent, status, resolvedLocation, candidates, error }`. It must not call Nearby Search. `resolvedLocation` is nullable and is never auto-filled solely because candidate count is one.

## 6. AMap POI text adapter

Add a server-only method backed by the already verified AMap POI text endpoint. Send the complete `rawQuery` first, request only the first page needed by v0.2A, and preserve provider order. Normalize `id`, `name`, `type`, `typecode`, administrative names, address, and location.

The adapter preserves safe `info`/`infocode` on provider errors through the existing `AmapApiError` path. It never returns or logs the key, Authorization headers, complete key-bearing URLs, or raw payloads. It does not add pagination, retries, a second provider, or a dynamic query-rewrite strategy.

## 7. Geocode address fallback

For `ADDRESS_QUERY`, call the existing geocode method and normalize the single provider result into `source: "geocode"`. Require valid coordinates. If geocode fails, return `not_found` or `error` with safe provider diagnostics; do not silently switch to a partial region query.

For a place query, geocode may be retained only as comparison/fallback evidence when the POI adapter has a capability failure and the result passes evidence checks. It must not override a better POI candidate silently.

## 8. Resolution-state API contract

Keep the request shape:

```json
POST /api/resolve-location
{ "query": "..." }
```

Return the smallest compatible evolution:

```ts
interface LocationResolutionResponse {
  query: string;
  intent: "PLACE_QUERY" | "ADDRESS_QUERY";
  status: "confirmed" | "needs_confirmation" | "not_found";
  resolvedLocation: LocationCandidate | null;
  candidates: LocationCandidate[];
  error: { message: string; info: string | null; infocode: string | null } | null;
}
```

Public errors are safe and do not include secrets, provider URLs, stack traces, or filesystem paths. Existing confirmed `/api/search` input remains key-free and rejects an unconfirmed or mismatched center.

## 9. Candidate normalization

POI candidates map AMap `id/name/type/typecode/pname/cityname/adname/address/location` to the normalized contract. Geocode maps the existing formatted address, level, administrative fields, and coordinates. Empty strings become `null`; invalid locations are isolated and do not fail the whole candidate set.

No typecode is hardcoded in router or UI code. Provider type/typecode are evidence fields and may be wrong upstream.

## 10. Deterministic evidence and confirmation

Evidence evaluation uses only visible query text and normalized provider fields:

1. reject malformed candidates;
2. reward exact/normalized subject-name matches;
3. reward explicit city/district matches and penalize explicit region conflicts;
4. reward compatible place type;
5. retain provider order as the final tie-break;
6. surface `needs_confirmation` for material conflicts, multiple plausible branches, or a single candidate lacking sufficient evidence.

For `深圳北站`, a train-station candidate may rank above bus/metro/entrance related candidates, but no Shenzhen-specific special case is allowed. For Hong Kong conflicts, a Chengdu candidate cannot be silently confirmed. No candidate is default-selected in the browser.

## 11. SearchApp state transitions

Replace the single implicit geocode success assumption with:

`initial → resolving → needs_confirmation | confirmed | not_found | resolve-error`

Candidate selection is local state. The confirm action copies the selected candidate into `resolvedLocation`; only then can the existing nearby-search action run. Existing `searching`, `results`, and partial-success behavior remain unchanged after confirmation.

The UI shows normalized name, place type, city/district, and address. Technical typecode and coordinates remain secondary/diagnostic. No modal, map, autocomplete, or visual redesign is introduced.

## 12. Inline candidate UX

For `needs_confirmation`, render an inline list of at most five provider-ordered candidates. Default selection is `NONE`; each candidate has a keyboard-accessible selection control and a separate confirm action. Empty candidates show an explicit not-found state. Confirmed state shows the selected candidate and keeps the existing “search nearby” affordance.

The UI must render missing optional values as omissions or friendly fallbacks, never `null`, `undefined`, or `NaN`.

## 13. Stale-state behavior

Any query change invalidates candidates, selected candidate, resolved location, and nearby results. In-flight resolve responses are ignored when their request token no longer matches. Changing query after selection always requires a fresh resolve. Existing confirmed-center equality validation remains the final server authority.

## 14. Error behavior

- malformed/empty query: existing 400 validation;
- POI provider error: safe `error` with `info`/`infocode`, no geocode downgrade that drops user intent;
- geocode provider error for an address: safe `error`/`not_found`;
- no usable candidates: explicit `not_found`;
- partial candidate normalization: keep valid candidates and record only safe diagnostics;
- ambiguous candidates: `needs_confirmation`, never first-result auto-confirmation.

- `香港城市大学` rejects the Chengdu region conflict;

- `广东省深圳市龙华区深圳北站` stays `PLACE_QUERY`;
- one candidate without strong evidence remains confirmation-required;
- no result and provider error preserve safe states and diagnostics;
- missing optional fields normalize to `null`;
- query mutation clears candidates/selection/resolution/results;
- confirmed search rejects a mismatched center;
- English and Chinese candidate names are not discarded by language alone.

All existing tests must continue passing. No assertions depend on live provider ordering.

2. Hong Kong City University does not silently confirm Chengdu and retains English POIs.
3. `澜庭酒店 深圳罗湖` keeps the hotel subject visible.

## 17. Migration sequence

1. Add location types, router, normalization, and evidence pure functions.
2. Add the isolated POI adapter method to the existing AMap client.
3. Add resolver service and service tests.
4. Extend the resolve route response while retaining `{ query }` input.
5. Update SearchApp state and inline candidate confirmation.
6. Adapt only the minimum search validation/types needed for the confirmed candidate.
7. Run automated checks, then desktop/mobile browser acceptance.

No data migration, deployment change, or API-key handling change is needed.

## 19. Risks and mitigations

- AMap type/typecode errors: expose them as evidence and require confirmation.
- Provider ordering changes: preserve ordering only as a tie-break; do not encode live order in tests.
- Hong Kong/overseas coverage differences: preserve safe provider errors and avoid silent fallback.
- Address/POI overlap: strong street/doorplate evidence gates address routing; province/city/district alone is insufficient.
- Stale asynchronous responses: request token invalidation and server center equality remain mandatory.
- Candidate noise: cap the initial list and use `needs_confirmation`, not blacklists or an ML score.
