# v0.1B-2 Plan

Status: `v0.1B-2A IMPLEMENT approved; v0.1B-2B not approved`

Scope: plan only. No v0.1B-2 implementation is authorized by this document.

## Current architecture

The v0.1B-1 baseline is stable and remains unchanged:

- Next.js App Router renders the page from `app/page.tsx`.
- `src/web/SearchApp.tsx` owns the two-stage client flow.
- `POST /api/resolve-location` geocodes a query on the server.
- `POST /api/search` accepts the confirmed centre, selected category ids, and radius, then calls the existing search service.
- `src/server/amap.ts` is the only server-side Key boundary.
- `src/search/service.ts` performs serial category requests with the existing interval and category-level error isolation.
- `src/amap/categories.ts` remains the source of truth for category labels, groups, typecodes, strategies, and price modes.
- `src/search/sort.ts` remains the only place that implements place comparison.

There is no new AMap capability, provider, API route, database, session, cache, or search-core redesign in this plan. The existing request contract already supports category ids and the allowed radii, so v0.1B-2 should stay client-focused.

## v0.1B-2 interaction design

The page keeps the existing order:

1. location input and resolve action;
2. resolved-location confirmation;
3. category selector;
4. radius selector;
5. explicit “search nearby” action;
6. local result filters, sort controls, and result list.

The initial selection is all eight category ids and radius `3000`. Category or radius changes never call AMap automatically. They invalidate the current result and show a short “please search again” state. Query changes continue to invalidate the resolved location and result as in v0.1B-1.

### Category selection

The eight fixed categories are grouped as:

- 住宿: `hotel`
- 购物: `mall`
- 餐饮: `hotpot`, `bakery`, `dessert`
- 娱乐: `ktv`, `billiards`, `gym`

The browser stores only `CategoryKey[]`. It never stores or submits typecodes, AMap keywords, or arbitrary category values. The selector provides:

- one checkbox/toggle per category;
- one toggle per group;
- 全选;
- 清空.

When no category is selected, the search button is disabled and a concise validation message is visible.

Group state is derived from its member ids. All selected means checked, none selected means unchecked, and a partial group is represented as mixed/indeterminate. Toggling a partial or unchecked group selects all members; toggling a fully selected group clears all members. The operation is a pure set transformation and preserves the canonical `CATEGORIES` order.

### Radius selection

The selector exposes only:

`1000`, `2000`, `3000`, and `5000` meters, displayed as 1/2/3/5 km. The default is 3000. Changing radius clears the old response and marks the page as needing a new explicit search. It never starts a background request.

### Stale-result policy

Any input that changes the eventual search request invalidates the result immediately:

- query: clear resolved location, response, and confirmation;
- resolved location: clear response;
- selected category ids: clear response;
- radius: clear response.

The UI should not retain an old result with a quiet warning. Clearing is less ambiguous and avoids implying that a newly selected category or radius was already searched. Category and radius changes do not require a new geocode while the resolved location remains valid. The user explicitly presses search again.

### Result filters

After a response, show an `全部` filter plus one filter for each category actually present in the response. Empty and error categories remain visible as filters so their state is discoverable; they show an empty or error message when selected and carry a non-color status marker. A filter change is local only and never calls `/api/search`.

### All / mixed results

`全部` merges `places` from successful categories only. Empty categories add no rows; error categories do not make the successful rows disappear. The merge is deduplicated by exact AMap `Place.id` using a `Map`. The first occurrence in response/category order is kept, including its category. No name, address, coordinate, or fuzzy matching is introduced. Single-category views do not perform cross-category deduplication.

### Sorting

The UI reuses `sortPlaces` and does not implement a second comparator. All/mixed views allow distance ascending and rating descending. A single category allows the modes already approved by `isSortModeAllowed`: distance, rating, and cost ascending/descending only for the configured sortable price modes. Hotel, mall, billiards, and gym do not expose cost sorting.

When the active filter changes and the current mode is not valid for that view, the mode immediately falls back to `distance-asc`. Sorting is always local and must not mutate the source array. Null ratings and costs remain last through the existing comparator.

### Local loading more

No API page 2 is added.

- Single-category view starts at 10 rows, then reveals 20, then at most the API-returned 25.
- `全部` starts at 20 and increases by 20 until all merged local rows are visible.
- The button disappears when the current local list is fully visible.
- Changing the active filter resets visible count to that view’s default (10 for one category, 20 for all).
- Changing sort within the same view preserves the current visible count.

## State model

Keep one page-level component state model using `useState` and `useMemo`; do not add Redux, Zustand, Context, or a reducer unless implementation reveals a concrete synchronization problem.

```text
query: string
phase: existing resolve/search phase union plus a needs-search presentation state if useful
resolvedLocation: GeocodedPlace | null
selectedCategoryIds: CategoryKey[]          // defaults to all eight
radiusMeters: SearchRadius                  // defaults to 3000
searchResponse: SearchResponse | null
activeFilter: "all" | CategoryKey
sortMode: SortMode                           // defaults to distance-asc
visibleCount: number                         // resets on filter/view changes
```

`selectedCategoryIds` remains the request source. `activeFilter`, `sortMode`, and `visibleCount` are view state. Response data is never duplicated into category-specific state.

## Derived state

Use `useMemo` for:

- selected category/group membership and group tri-state;
- filters available from the response;
- active category status and local source places;
- merged/deduplicated all places;
- valid sort options for the active view;
- fallback sort mode;
- sorted places;
- visible places and `hasMore`;
- total result count and successful/empty/error category counts.

Derived arrays must not be written back into state. A new response resets `activeFilter` to `all`, `sortMode` to distance, and `visibleCount` to the all-view default.

## Component tree

Keep the tree shallow and page-oriented:

```text
Page
└─ SearchApp

   ├─ CategorySelector

   │  └─ CategoryGroup
```

Components may remain in a small number of files; do not create a general design system or front-end domain layer.

- `selectAllCategories()` and `clearCategories()`

- `invalidateSearchState(reason)` if a pure transition helper makes the stale policy clearer

- `getAvailableFilters(response)`
- `getSortOptions(view)` and `ensureValidSortMode(mode, view)`

`sortPlaces` and `isSortModeAllowed` remain reused from `src/search/sort.ts`; their comparator is not copied into the UI.

## Responsive strategy

Desktop targets a roughly 960–1080px content width. Controls stay compact and results use dense rows with name, distance, rating, cost, tag, and address visible at a glance.

Mobile keeps the input full width, lets category controls wrap or collapse without introducing a new complex component, uses reachable radius controls, permits horizontal scrolling only inside a filter strip if required, and renders one-column result rows. No page-level horizontal overflow, hover-only action, or tiny touch target is acceptable.

## Accessibility strategy

- Use `label` for the location input and radius control.
- Use `fieldset`/`legend` or equivalent group semantics for categories and radius.
- Use real checkbox/button semantics for category and group toggles.
- Expose group mixed state with native indeterminate behavior or equivalent `aria-checked="mixed"`.
- Preserve keyboard navigation and visible focus styles.
- Use `aria-busy` during resolve/search and `aria-live` for result summaries/loading/errors.
- Do not convey empty/error/selected state by color alone.
- Mark the active filter and selected sort mode with text/state semantics.

No accessibility library is planned.

## Risks

| Risk | Mitigation |
|---|---|
| Category/radius changes leave old results visible | Clear response immediately and require explicit search. |
| All view duplicates one POI across categories | Exact id `Map` dedupe only; keep first response occurrence. |
| Cost sort remains visible for unsupported categories | Derive options from active view and existing price-mode policy; fallback to distance. |
| Empty/error categories disappear from navigation | Keep them as filter items with explicit status and local empty/error content. |
| Visible count becomes inconsistent across filters | Reset on filter change; derive defaults from view kind. |
| UI reimplements comparator semantics | Delegate all sorting to `sortPlaces`. |
| Mobile controls create horizontal overflow | Test narrow viewport and constrain scrolling to local filter controls only. |
| Page state becomes too coupled | Keep pure selection/result/formatter helpers small and avoid global state. |
