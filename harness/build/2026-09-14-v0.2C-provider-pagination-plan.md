# v0.2C / P0-2 Search Coverage & Provider Pagination Plan

状态：`V0.2C_LOCAL_VERIFICATION_PASS` / `AWAITING_LIVE_PROVIDER_VERIFICATION_AUTHORIZATION`

本文件记录已获实施授权后的范围与验证结果。实现已通过本地测试、类型检查和生产构建；未进行真实 Provider 调用、提交、推送或部署。

## 1. 目标

在不改变现有地点解析、初始周边搜索、类别策略和排序语义的前提下，让用户能够针对一个具体类别显式获取 AMap Around Search 的第 2 页，从而把单类别可获取结果从最多 25 条扩展到最多 50 条。

本增量优先保证：

- 初始搜索延迟与请求量不回归。
- Provider 翻页由用户明确触发，不自动预取。
- 第 2 页失败不会破坏第 1 页结果。
- 浏览器不能控制任意 Provider 页码、页大小、关键词、typecode 或 Key。
- 变更小、可离线测试、可独立回滚。

## 3. 范围与非目标

### 3.1 本计划允许的后续实现范围

- 单个具体类别的 AMap Around page 2 请求。
- 单类别搜索时，All 作为唯一类别别名请求 page 2。
- page 1 与 page 2 的精确 ID 去重、合并和重新排序。
- page 2 的 loading、非破坏性 error 与 exhausted 状态。
- 与上述行为直接相关的最小 API、状态和测试。

### 3.2 明确不做

- page 3 或更深页码、通用分页框架、无限滚动。

- AMap photos、地图、收藏、数据库、用户历史。
- 新 Provider、AI ranking、推荐、reviews、hotel offers。
- fuzzy name/address dedupe、坐标相似度去重或实体解析。
- 大型状态管理、scheduler、并发队列、自动重试。
- 视觉重设计、Vercel、DNS 或 Production 配置修改。

## 4. 产品硬边界

```ts
const MAX_PROVIDER_PAGE = 2;
const PROVIDER_PAGE_SIZE = 25;
```

- page 1 是现有初始搜索。
- page 2 是唯一允许的用户驱动扩展。
- v0.2C 不存在 page 3。
- `MAX_PROVIDER_PAGE = 2` 是产品侧边界，不是对 AMap 技术上限的声明。
- Provider page number 和 page size 均由服务端拥有，不由浏览器选择。

## 5. Display load more 与 Provider load more

两种操作必须在代码和测试中保持分离：

### 5.1 Display load more

只增加 `visibleCount`，显示已经存在于 `SearchResponse` 中的地点，不产生网络请求。

### 5.2 Provider load more

只有当当前类别已经显示完本地结果、page 1 是满页且仍符合产品条件时，用户的明确操作才调用应用自有的 page endpoint，服务端再请求 AMap page 2。

页面可以使用同一区域承载两个动作，但判断顺序必须是：

1. 本地仍有未显示结果：执行 display load more。
2. 本地结果已全部显示且允许 page 2：执行 Provider load more。
3. 不满足以上条件：不显示可执行的 load-more action。

Provider page 2 成功后应立即展示下一批结果，避免用户点击后列表没有可见变化。单类别建议保持现有节奏并扩展为 `10 → 20 → 25 → 35 → 45 → 50`；page 2 获取成功时从 25 增加到最多 35。

## 6. 最小 API 设计

新增：

`POST /api/search/page`

请求体固定为：

```ts
interface SearchSecondPageRequest {
  center: {
    longitude: number;
    latitude: number;
  };
  categoryId: CategoryKey;
  radiusMeters: SearchRadius;
}
```

请求不得包含：

- `resolvedLocation`
- `pageNumber`
- `pageSize`
- API Key
- keyword、types、strategy 或其它 Provider raw parameters
- 多个 category IDs

服务端固定：

```ts
pageNumber = 2;
pageSize = 25;
```

建议成功响应：

```ts
interface SearchSecondPageResponse {
  categoryId: CategoryKey;
  page: PlacePage;
}
```

安全边界：

- `categoryId` 必须来自现有 8 类配置。
- `radiusMeters` 继续只允许 `1000 | 2000 | 3000 | 5000`。
- 坐标沿用现有有限数值和地理边界校验。
- API route 不接受任意 page number 或 page size。
- Provider 错误保留在服务端诊断边界；浏览器只收到现有风格的安全通用错误。
- endpoint 不重新 geocode，不修改 resolver 或初始 `/api/search` contract。

## 7. Service primitive

后续实现应增加一个明确针对 v0.2C 的单类别第二页 primitive，而不是把初始多类别搜索改造成通用分页引擎。

职责：

1. 使用已验证的中心点、一个 category config 和 radius。
2. 调用 `searchNearby(center, category, { pageNumber: 2, pageSize: 25, radiusMeters })`。
3. 返回标准 `PlacePage`。
4. 不执行 geocode。
5. 不自动重试。
6. 不改变初始 `searchCategoriesSequentially()` 的 page 1/25 和类别间 500ms 行为。

## 8. 类别与 All 语义

Provider page 2 允许发生于：

### A. 具体类别 filter

`activeFilter !== "all"`，并且该类别 page 1 成功、满页、尚未获取 page 2、当前没有相同请求 in flight。

### B. 单类别搜索的 All

原始 search request 只有一个 `categoryId` 且 `activeFilter === "all"`。All 继承唯一类别的 Provider load-more 能力。

### C. 多类别搜索的 All

原始 search request 包含多个类别且 `activeFilter === "all"` 时：

- 继续允许现有 display load more。
- 不允许 Provider load more。
- 不批量获取所有类别 page 2。
- 不猜测应该扩展哪个类别。
- 本地结果全部显示后，可使用最小提示引导用户切换到具体类别继续获取。

判断必须基于原始 search request 的 category IDs，不能基于成功、非空或当前可见类别数量。

若用户已在具体类别获取 page 2，切回 All 后可使用这些已经获取的数据；不为 All 额外发请求，也不做类别配额平衡。

## 9. 跨页与 All-filter dedupe

`ALL_FILTER_DEDUPE_POLICY`：跨 Provider page merge 与 All-filter category aggregation 必须使用同一个 exact-ID identity rule。

- 非空 AMap `Place.id` 是唯一的精确 dedupe identity。
- page 1 已存在相同非空 ID 时，page 2 的重复项不追加。
- All-filter 聚合多个类别时，相同非空 ID 仍只保留第一项。
- `id.trim() === ""` 的地点永远不加入 `seenIds`。
- page 1/page 2 合并中的多个空 ID 地点必须全部保留。
- All-filter 聚合中，同一类别或不同类别的多个空 ID 地点也必须全部保留。
- 该规则同时适用于 page-1/page-2 merge 与现有 All-filter category aggregation，不能只修复其中一条路径。
- 实施时可以最小修改 `mergeSuccessfulPlaces()`，或增加一个很小的 shared exact-ID dedupe helper；以实际 diff 更小、重复更少者为准。
- 不增加名称、地址、坐标或 typecode 模糊规则。

合并必须是 immutable，不能修改原始 page 1 array。

## 10. Sorting

page 2 成功后的顺序固定为：

```text
page 1 places
+ page 2 places
→ exact non-empty-ID dedupe
→ existing global sort
→ visible slice
```

不得把 page 2 卡片固定追加在 UI 底部。继续复用现有：

- distance ascending
- rating descending，null last
- category-allowed cost ascending/descending，null last
- 现有 tie-break

不修改 `sortPlaces()` comparator。

## 11. Page-2 failure semantics

`PAGE_2_FAILURE_IS_NON_DESTRUCTIVE`

page 1 成功而 page 2 失败时：

- 保留所有 page 1 places。
- 不替换整个 `SearchResponse`。
- 不把类别从 `success` 改为整体 `error`。
- 不把原始搜索改成 `partial success`。
- 不推进已成功页号。
- 只记录当前类别的 pagination/load-more error。
- 显示安全、非阻塞的加载更多错误。
- 可以允许用户之后主动重试。
- 不自动重试，不后台重试，不建立 retry scheduler。

page-2 loading/error 状态必须与初始搜索 error 状态分开。

## 12. Exhaustion 与停止语义

### 12.1 硬停止

- 成功请求 page 2 后，无论 Provider 是否暗示还有数据，都因 `MAX_PROVIDER_PAGE = 2` 停止。

### 12.2 本地 exhaustion signals

- page 1 `returnedCount < pageSize`：不展示 page-2 action。
- page 1 `mayHaveNextApiPage === false`：不展示 page-2 action。
- page 2 empty：保留 page 1 并标记 Provider expansion exhausted。
- page 2 short：标记 exhausted。
- merge 后没有新增非空 ID：视为重复页信号并标记 exhausted。
- Provider failure：结束本次操作，但保留主动重试可能。
- stale response：直接忽略，不改变任何当前分页状态。

`mayHaveNextApiPage = returnedCount === pageSize` 只是本地 heuristic。短页、空页或 `mayHaveNextApiPage=false` 不得被描述为 AMap 对后续数据不存在的正式保证。

## 13. 官方 Provider facts

当前治理依据为高德开放平台官方“搜索 POI 2.0”文档：

- `page_size`：1–25。
- `page_num`：请求页号，默认 1。
- 相同参数翻页：最多支持获取 200 条数据。
- `count`：单次请求实际返回的 POI 数量。
- 独立明确的 `page_num` hard maximum：`NOT_FOUND / AMBIGUOUS`。
- short page 是否正式保证没有后续数据：`NOT_FOUND / AMBIGUOUS`。
- QPS：以当前账号控制台的配额管理为准，不在代码或计划中假定固定数字。

旧版或其它产品文档出现的 `page_num/pageIndex 1–100` 不作为当前 Web Service POI 2.0 Around contract，除非明确标注其旧版本或不同产品上下文。

官方参考：

- https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch
- https://lbs.amap.com/api/webservice/guide/tools/flowlevel

## 14. Request 与 rate behavior

初始搜索保持：

- 8 个选中类别 = 8 个 Provider requests。
- 类别串行。
- 7 个类别间隔 × 500ms = 最少 3.5 秒 intentional delay。
- Provider/network latency 另计。

page 2：

- 一次明确用户操作只产生一个 Provider request。
- 不 prefetch，不 batch 所有类别，不增加 scheduler 或 concurrency framework。
- 相同类别 page-2 请求进行中时必须禁止重复点击或重复发出。
- page-2 请求结束前维持明确 loading 状态。
- 由于一次 endpoint invocation 只有一个 Provider call，不在服务端虚构无意义的 category delay。

## 15. Stale response behavior

优先复用 SearchApp 现有 `requestId`：

- 发起 page 2 时捕获当前 request ID 和当前 search scope。
- location、radius、category selection 变化或启动新搜索时，现有 mutation path 增加 request ID 并清除旧结果。
- page-2 response 只有在 request ID 与当前 search scope 均仍匹配时才可 merge。
- stale success 和 stale failure 都不得覆盖新状态。
- 不引入新的取消框架或状态管理库。

## 16. Browser state 与最小交互

优先在现有 `SearchResponse` 中以 immutable 方式更新目标 `CategorySearchResult`：

- `places` 保存 page 1 + deduplicated page 2。
- `page` 保存最后一次成功 Provider page 的 metadata。
- page 2 empty 也可记录为成功到达 page 2，并停止后续 expansion。

新增的最小临时状态预计只有：

- 当前正在加载 page 2 的 category，或等价 in-flight guard。
- 每类别 pagination error。
- 必要时每类别 exhausted 标志；若可从最后成功 page 和硬上限可靠推导，则不重复存储。

UI 不重设计。只需明确 loading、非阻塞 error、具体类别“获取更多附近结果”，以及多类别 All 的最小引导。

## 18. Minimal test matrix

### Existing behavior regression

- 初始多类别搜索仍固定每类别 page 1/25。
- 类别串行顺序、500ms 间隔和单类别错误隔离保持。
- 当前 resolver、filter、sort、dedupe 和 stale invalidation 测试继续通过。

### Contract / validation

- page endpoint 固定调用 page 2/25。
- 合法 center/categoryId/radius 通过。
- 未知类别、非法 radius、越界/非有限坐标拒绝。
- `resolvedLocation`、`pageNumber`、`pageSize`、key、keyword、types 和额外字段拒绝。

### Service / merge

- page 2 success 返回标准 PlacePage。
- page 2 duplicate non-empty IDs 被去除。
- 多个 empty-ID places 不互相折叠。
- page 2 empty/short 正确标记 exhausted。
- page 2 全部是既有非空 ID 时无新增结果并停止。
- page 2 failure 保留 page 1、类别 success 和原始 SearchResponse status。
- merge 后执行现有 global sort；四种允许 sort mode 均覆盖。

### Web behavior

- 具体类别在本地结果显示完后才能触发 Provider page 2。
- 单类别 All 可以触发唯一类别 page 2。
- 多类别 All 只能 display load more，绝不触发 Provider page 2。
- 单类别 All 在 page-2 merge 后，多个不同的 empty-ID places 仍全部保留。
- 多类别 All 聚合时，不同类别的 empty-ID places 不互相折叠。
- All 聚合中重复的非空 ID 继续按精确 identity 去重。
- page 2 成功后同次操作显示新结果。
- 相同类别重复点击/in-flight 请求只发出一次。
- location/radius/category/new search 使旧 page-2 success/error 失效。
- page 2 error 显示为非阻塞状态，可后续主动重试，无自动 retry。

所有单元和 route tests 使用 fetch/client stub，不访问 live Provider。

## 20. Acceptance criteria

进入最终验证前必须同时满足：

1. 初始搜索继续是每类别 page 1/25，没有 eager page 2。
2. page endpoint 不接收任意 page number/page size/provider parameters。

10. tests/check/build/diff check 全部通过。
11. 不修改照片、resolver、Provider category strategy、Vercel 或 DNS。

## 21. Rollback

v0.2C 实施必须保持一个可独立回滚的增量：

- 删除 page endpoint 与 page-2 contract/service primitive。
- 移除 SearchApp 的 Provider load-more state 和 action。
- 恢复原 `visibleCount` 仅展示 page 1 结果的行为。
- 不需要迁移数据、清理数据库、恢复 Provider 配置或修改部署环境。

## 22. 已知风险与待复核点

- 官方没有给出当前 POI 2.0 的独立 `page_num` 最大值；本计划使用产品硬上限 2。
- 满 25 条只表示本地“可能有下一页”，可能请求到空 page 2。
- Provider 可能跨页返回重复或顺序变化，必须精确 ID dedupe 后重排。
- 空 ID 无稳定 dedupe identity，只能保留，不能猜测实体相同。
- 用户在具体类别加载 page 2 后，All 的类别占比可能不均衡；v0.2C 不做平衡算法。
- QPS 取决于账号控制台；本计划通过显式单请求、无预取和 in-flight guard 降低单会话突发。
- page 2 主动重试的具体文案属于 STEP 3 最小 UX 决定，不得演变成 retry framework。
