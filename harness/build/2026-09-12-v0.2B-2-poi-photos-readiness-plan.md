# v0.2B-2 POI Photos Readiness Plan

状态：`V0.2B_2_PHASE_B_EVIDENCE_COMPLETE` / `V0.2B_2_PHASE_C_AUTHORIZATION_AMBIGUOUS` / `V0.2B_2_PRODUCTION_PHOTO_IMPLEMENTATION_BLOCKED`

## 1. 目标

本计划只验证 AMap POI photos 是否具备进入后续生产设计的证据基础，不实现图片 UI、不改变生产 provider request、不扩展生产 `Place` contract。

需要回答：

1. 深圳与香港 8 类 POI 的真实照片覆盖率是否足够稳定。
2. 图片内容是否与 POI 相关且适合紧凑 result card。
3. 缺图、坏 URL、低质量图的失败模型如何处理。
4. 当前账号和产品场景是否有展示、hotlink、proxy、cache 或持久化授权。
5. 若全部通过，最小 production contract 和图片交付方式是什么。
6. 若授权或证据不足，是否继续保持 provider photos blocked。

## 2. 当前证据

- 现有隔离脚本：`scripts/spikes/result-card-enrichment-spike.ts`。
- 脚本已经以 `show_fields=business,navi,photos` 构造 POI 2.0 Around 请求，并且不输出完整图片 URL、Key 或 raw response。
- 之前的 photos Spike 没有真实 Key，深圳与香港 16 个类别样本均为 `NOT_RUN`，结论为 `RESULT_CARD_ENRICHMENT_NOT_READY`。
- 现有生产 `Place` 只有 name、category、distance、rating、cost、tag、address、longitude、latitude；没有 photos 字段。
- 当前“查看位置” marker link 与 v0.2B-1 结果卡片已稳定，不在本计划中重做。

## 3. 范围与非目标

本计划允许：隔离 Spike、脱敏统计、有限人工视觉复核、授权证据收集、条件式 production design proposal。

明确不做：

- 生产 UI 图片卡片、gallery、carousel 或图片交互。
- 修改生产 AMap client、`/api/search`、Nearby Search 语义或 QPS 策略。
- 修改生产 `Place` contract 或向浏览器透传 provider raw photos array。
- 新 Provider、数据库、图片 CDN、用户上传、审核流水线、LLM 或 image-generation fallback。
- P0-2 provider pagination、hotel nightly price、review count、realtime opening status、favorites、map SDK、navigation 功能。
- 任何 DNS、Vercel、Production 环境变量或部署操作。

## 5. Phase A：Live Coverage Replay

### 5.1 执行边界

- 只复用 `scripts/spikes/result-card-enrichment-spike.ts` 的隔离路径；不修改生产 client。
- 真实 Key 仅从 `process.env.AMAP_WEB_SERVICE_KEY` 读取。
- 请求串行执行；相邻 Around 请求之间等待约 500ms，无 retry、退避、并发队列或 scheduler。
- 不打印 Key、完整 secret-bearing URL、完整 photo URL 或 raw provider response。
- 输出仅包含脱敏统计与必要的 POI 名称/type/typecode；如需标识 URL，只记录协议、host 分类和布尔值。

### 5.2 安全 anchor

使用已经验证过的地点中心，避免裸地点歧义：

1. 深圳北站区域：以已确认的深圳北站坐标为中心。
2. 香港城市大学区域：使用结构化输入 `香港特别行政区九龙达之路香港城市大学`，并以已确认的香港候选坐标为中心。

如果脚本需要 geocode，必须先验证地区，错误匹配不得继续 Around；也可以直接使用已确认中心，避免重复 geocode。

### 5.3 2×8 evidence matrix

| 地点 | hotel | mall | hotpot | bakery | dessert | KTV | billiards | gym |
|---|---|---|---|---|---|---|---|---|
| 深圳北站区域 | 1 row | 1 row | 1 row | 1 row | 1 row | 1 row | 1 row | 1 row |
| 香港城市大学区域 | 1 row | 1 row | 1 row | 1 row | 1 row | 1 row | 1 row | 1 row |

每个地点/类别至少记录：

- provider status、info、infocode（脱敏日志允许保留这些诊断字段）；
- returned POIs；
- POIs with photos / without photos；
- photo coverage ratio；
- total photo objects；
- HTTPS URL count；
- malformed photo shape count；
- photo host distribution（仅 host，不记录完整 URL）；
- empty-photo 与 request error 状态。

不得仅输出 overall percentage；必须保留每个地点和类别的独立行。

## 6. Coverage 判定

本计划不预先设置武断的百分比阈值。Phase A 只负责证据收集，Phase B/C 完成后再决定 production threshold。

必须比较：

- 深圳 vs 香港总体差异；
- 每个类别 coverage、空图率、坏 shape 率、HTTPS 比例；
- 是否存在几乎没有图片的类别；
- 同一类别跨地点是否极不稳定；
- 返回数量很少导致的统计置信度问题。

低 coverage 不自动判失败，但必须明确标记为 partial evidence；若无法支撑“真实照片为默认卡片内容”的产品假设，保持 blocked/partial。

## 7. Phase B：Manual Visual Relevance Review

### 7.1 抽样方式

- 每个地点/类别最多抽样 3 个有图 POI；总上限 48 个 POI，避免图片数据库化。
- 优先抽样列表前排和不同 photo host 的样本；不下载或持久化全部图片。
- 仅在浏览器临时查看，评审后不保存图片文件或完整 URL。

### 7.2 记录维度

每张抽样图标记为：

- `relevant`：确实对应该 POI/门店，适合 result-card crop；
- `acceptable_but_weak`：相关但画面弱、logo-only 或信息密度低；
- `irrelevant`：与 POI 不匹配、广告/菜单/二维码等；
- `unusable`：损坏、过低质量、异常或包含明显敏感内容。

同时记录是否存在：

- 误配到其它门店的图；
- 仅 logo、海报、菜单、二维码图；
- 低分辨率或加载失败；
- 不适合固定 aspect ratio crop 的构图；
- 明显敏感或异常内容。

人工复核只评价样本，不把主观印象扩展成全量保证；证据不足时使用 `NEEDS_MORE_DATA`。

## 8. Image failure model

后续设计必须接受 photos 非 100% 存在：

- 有效 provider photo：才允许显示真实图；
- 缺图、非 HTTPS、坏 shape、加载失败或授权不明：使用本地类别视觉 fallback；
- fallback 必须明确是 UI decorative fallback，不得伪装成真实店铺照片；
- 缺图不得隐藏 POI、改排序、改变 provider semantics 或降低其结果资格。

## 9. Phase C：Authorization / Usage Rights Gate

API response 中存在 `photos` 字段，只能证明技术可取，不等于产品获得展示权。需要账号/官方文档/支持渠道的明确证据，逐项确认：

- 直接 hotlink 到 provider URL；
- 浏览器直接加载外部图片；
- 服务端 proxy；
- 临时内存/边缘缓存；
- 持久化缓存或对象存储；
- resizing、cropping、格式转换；
- CDN 转发；
- 是否要求“数据来源：高德地图”等 attribution；
- 商业使用、公开展示、跨境访问或其它地域限制。

本计划不替用户做法律结论。缺少明确授权证据时，状态必须是：

`V0.2B_2_PHOTOS_BLOCKED_BY_AUTHORIZATION`

不得以署名、`noreferrer`、短期缓存或“仅展示 URL”推定已获授权。

## 10. Attribution Gate

若授权明确允许展示，仍需确认结果卡片或 results section 是否必须显示“数据来源：高德地图”或其它 attribution。Attribution 是独立要求，不能替代图片展示权。

## 11. Phase D：条件式 production design proposal

只有 coverage、visual relevance、authorization、attribution 均通过，才允许形成实现方案。默认最小形状：

```ts
photo?: {
  url: string;
  title?: string;
}
```

这是候选方案，不是本阶段要加入的 production contract。浏览器只能收到归一化、校验后的单张代表图，不得透传 raw photos array、provider response 或凭据。

第一版最多每个 POI 一张代表图；不做 gallery、carousel、多图查看器或 AI 选图。若证据不足，继续保持 `Place` 不变。

## 12. Photo selection proposal

若未来进入实现，候选 deterministic 规则为：按 provider 返回顺序选择第一张通过 HTTPS、URL 解析、允许 host 策略和非空校验的图片。该规则必须在 Phase A/B 证据后确认；不能在没有真实样本时预设图片一定相关。

## 13. 图片交付策略比较

| 方案 | 优点 | 风险/成本 | 本计划结论 |
|---|---|---|---|
| plain `<img>` | 最小改动、无额外 remote host 配置 | 浏览器直连、referrer/CSP/授权与跨域行为需确认 | 若授权允许且 host 稳定，可作为候选 |
| `next/image` | 优化与尺寸控制较好 | remotePatterns、缓存、优化器请求和授权边界更复杂 | 需要额外验证，不作为默认 |
| server proxy | 可统一校验、隐藏 provider host、控制缓存 | 新增代理面、带宽/缓存/授权责任 | 只有明确授权且有必要时再评估 |

在授权和 host 行为不明确时，不选择任何方案进入生产。

## 14. Security considerations

未来方案必须覆盖：

- 仅允许 HTTPS；
- URL 解析与 host 策略校验；
- malformed URL 安全失败；
- 不把图片 URL 当作 HTML 注入内容；
- `alt`/title 以文本安全渲染；
- 不将 `AMAP_WEB_SERVICE_KEY` 拼入图片 URL；
- 评估 referrer、CSP、跨站请求和第三方 host；
- provider secret 与浏览器 contract 分离；
- 图片加载失败不泄漏 provider 原始错误或 stack。

## 15. Performance considerations

一次 Nearby Search 可能返回大量 POI，不能给每一条结果默认加载远程图片。后续若获批，至少需要：

- 只为当前已 reveal 的结果加载图片；
- 使用原生 lazy loading 或等价轻量策略；
- 设定可见图片数量预算；
- 图片失败快速回退；
- 不引入 virtualization、复杂预取或后台批量下载。

## 16. Responsive considerations

条件式设计需分别评估 1024px+ 与 375/390/430px：

- 固定或受限 aspect ratio；
- `object-fit` 与裁剪策略；
- 长 POI 名称与图片并存；
- metadata 稀疏时的卡片高度；
- 缺图 fallback 与有图卡片视觉一致性；
- 有图不能造成卡片高度失控或页面横向溢出。

本阶段不写 CSS、不修改现有稳定视觉。

## 17. Checkpoints

### Checkpoint A：Coverage evidence

验收 2×8 矩阵、脱敏输出、协议与 host 统计；失败即 `PHOTO_COVERAGE_EVIDENCE_INSUFFICIENT` 并停止。

### Checkpoint B：Visual relevance

完成有限抽样并记录四级标签；若明显无关/不可用图片占比或类别差异无法解释，停止并保持 partial/not ready。

### Checkpoint C：Authorization and attribution

每一种拟议交付方式均有明确授权证据；否则 `V0.2B_2_PHOTOS_BLOCKED_BY_AUTHORIZATION`。

### Checkpoint D：Design proposal

只在 A/B/C 通过后提出最小 contract、选择规则、fallback、性能与响应式方案；不实现。

### Checkpoint E：Implementation approval

人工复核最终 proposal 后，才可决定 `V0.2B_2_PHOTOS_IMPLEMENTATION_APPROVED`。本计划不会自动进入 IMPLEMENT。

## 18. Failure / stop conditions

- 缺少 `AMAP_WEB_SERVICE_KEY`：立即停止，不发请求。
- 任何日志包含 Key、完整 secret-bearing URL、完整 photo URL 或 raw response：立即停止并清理暴露产物。
- provider error、QPS、地区权限或字段限制：保留脱敏 info/infocode，停止对应矩阵行，不伪造数据。
- 真实照片 coverage、相关性或 host 稳定性不足：保持 `RESULT_CARD_ENRICHMENT_PARTIAL` 或 `NOT_READY`。
- 授权证据不足：保持 `V0.2B_2_PHOTOS_BLOCKED_BY_AUTHORIZATION`。
- 任何生产代码、生产 contract 或稳定 UI 被要求修改：停止，回到审批。

## 19. Rollback

本阶段没有生产实现，因此 rollback 是删除或隔离临时 Spike 输出与未提交研究产物；不得回滚生产代码、部署、DNS 或环境变量。若未来实现获批，必须使用独立提交，可整体 revert，不与 pagination、favorites 或其它版本混合。

## 21. Exact acceptance criteria

Plan review 通过必须确认：

1. 2×8 live matrix 已定义，且使用安全 anchor、串行请求与约 500ms 间隔。
2. 缺 Key、QPS、地区权限和 malformed photo 均有停止条件。
3. 输出不会包含 Key、完整 secret-bearing URL、完整 photo URL 或 raw response。
4. coverage 以地点/类别分别统计，不预设武断阈值。
5. visual relevance 有 bounded manual review 和四级结果。
6. 缺图 fallback 不伪造图片、不隐藏 POI、不改排序。
7. authorization 与 attribution 是独立 gate。
8. `Place` contract 只有在所有前置 gate 通过后才提出最小候选扩展。
9. plain `<img>`、`next/image`、server proxy 的差异已记录，未提前实现。
10. 性能、响应式、安全、回滚和未来 implementation approval 均有边界。

## 22. Final outcome options

Phase A–C 完成后只能选择一个：

- `RESULT_CARD_ENRICHMENT_READY`：coverage、visual relevance、authorization 与 attribution 均有足够证据，可进入独立 implementation approval。
- `RESULT_CARD_ENRICHMENT_PARTIAL`：部分类别/地区有证据，但 coverage、相关性或授权仍有明确限制；继续保持生产 photos 不接入。
- `RESULT_CARD_ENRICHMENT_NOT_READY`：证据不足、图片质量不可接受或授权不可确认。

当前计划不预设 outcome，等待人工批准后才可执行 Phase A。
