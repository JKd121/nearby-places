# v0.2A Location Intent Resolution Plan

Status: `REVIEWED`

This is a plan-only document. It does not authorize implementation, real API calls, UI changes, provider pagination, or any v0.2 feature outside location intent resolution.

## 1. Scope and stable baseline

The v0.1C deployment is complete and remains the production baseline. The only new problem in scope is correct interpretation of a user's requested place before Nearby Search starts.

In scope:

- candidate-oriented location resolution;
- preserving the complete raw query;
- deterministic comparison of entity, region, type, and clue matches;
- explicit `confirmed`, `needs_confirmation`, and `not_found` resolution states;
- minimal compatible changes to the resolve contract and browser state;
- regression and real-browser verification for the four known failure classes.

Frozen for v0.2A:

- provider result pagination beyond the first 25 results;
- nearby result pagination/load-more changes;
- favorites, accounts, database, maps, navigation, hotel pricing, custom categories, second providers, AI/LLM, search templates, ranking redesign, and visual redesign.

No v0.2A work may change the accepted AMap nearby-search category strategy, QPS interval, local distance calculation, sorting, filtering, dedupe, or production DNS/deployment.

## 2. Current resolver architecture

### Repository preflight

The accepted v0.1C baseline is on `master` at the previously pushed deployment history. The current working-tree changes for this turn are Harness documentation only: this new plan and the `PLANS.md` state update. No application source, tests, deployment configuration, DNS, or production environment has been changed. The v0.1C private GitHub remote and custom-domain deployment remain the stable baseline.

Current request path:

```text
Browser query
  → POST /api/resolve-location { query }
  → route validates only query
  → createServerAmapClient().geocode(query)
  → GET AMap /v3/geocode/geo
  → client takes geocodes[0]
  → { resolvedLocation }
  → browser displays one location
  → user confirms
  → POST /api/search { center, resolvedLocation, categoryIds, radiusMeters }
```

Current code evidence:

- `app/api/resolve-location/route.ts` accepts only `query`, trims it, and returns the result of one `geocode` call.
- `src/server/amap.ts` creates a server-only client from `process.env.AMAP_WEB_SERVICE_KEY`.
- `src/amap/client.ts` calls the AMap geocoding endpoint and selects the first item in `payload.geocodes`; it does not retrieve or rank candidates.
- `GeocodedPlace` contains query, formatted address, province/city/district, level, and coordinates, but no provider place id, place type, typecode, or candidate list.
- `src/search/validation.ts` requires a single `resolvedLocation` and exact center-coordinate equality for confirmed search.
- `src/web/SearchApp.tsx` renders one “已解析位置” block and has no candidate-selection state.
- `src/search/service.ts` already keeps the confirmed center separate from geocoding and must remain unchanged during the Spike.

## 3. Root-cause analysis of known failures

### P0-1A: same-name ambiguity

The resolver discards every result after `geocodes[0]`. A query such as `维也纳酒店` can have several legitimate branches, but the current contract cannot represent “several plausible places” and the UI cannot ask the user to choose.

### P0-1B: regional mis-match

Geocoding is being treated as an authoritative place-name resolver. The observed `香港城市大学` → Chengdu result shows that the first geocode result can be geographically incompatible with the user's apparent clue. The current generic Hong Kong Smoke Test guard is not a general resolver and is not part of the browser contract.

### P0-1C: entity/type/layer mis-match

`深圳北站` is returned as a single coordinate with no visible provider type. A train-station parent, bus stop, metro station, parking area, and entrance can share the same name stem. Without `type`/`typecode` or an explicit candidate list, the browser cannot distinguish the requested main entity from a related sub-place.

### P0-1D: multi-clue intent loss

The current path sends `澜庭酒店 深圳罗湖` as one geocoding string and has no model for subject plus city plus district. Provider ranking can therefore favor an administrative area or later address clue. Nothing in the current contract records that “澜庭酒店” is the subject and “深圳/罗湖” are constraints. The system has no explicit protection against returning a district unrelated to the named hotel.

### Common failure

All four failures come from the same design assumption: `query → one geocode result → coordinate`. There is no candidate retrieval, no intent evidence evaluation, no type visibility, and no safe unresolved state. The fix must address those missing states rather than add a blacklist for individual POIs.

## 4. Minimum Location Intent model

The model is conceptual for this plan and must remain small:

```text
LocationIntent {
  rawQuery: string                 // immutable source of truth
  subjectText: string | null       // named entity, if deterministic extraction is safe
  placeTypeClue: string | null     // hotel, station, university, etc., if present
  cityClue: string | null
  districtClue: string | null
  branchOrSubEntityClue: string | null
  structuredAddressClue: string | null
  nearbyLandmarkClue: string | null
}
```

Rules:

- `rawQuery` is always retained and is the source of truth.
- Any extracted clue is supplementary; extraction failure must not delete or rewrite the raw query.
- Extraction is deterministic and conservative: trim/collapse whitespace, normalize safe punctuation/full-width variants, and compare visible text. Do not add an NLP framework, translation service, LLM, embeddings, or a broad administrative-rule engine.
- A token is a clue only when the provider result or a small existing vocabulary gives evidence for it. The plan must not invent an entity from an arbitrary city/district word.
- Subject and region are conjunctive when both are present. A failed subject match must not silently turn `澜庭酒店 深圳罗湖` into a search for `深圳罗湖`.

## 5. Proposed provider strategy

The Spike must compare two provider paths without changing the production resolver yet:

1. **Current Geocoding baseline**: the existing AMap geocode request and its first-result behavior, captured as the baseline only.
2. **Candidate-oriented place search**: an AMap POI/place keyword-text search capability supported by the current Web Service key, evaluated for returning multiple named entities with `id`, `name`, `type`, `typecode`, administrative fields, address, and location. The exact endpoint and accepted parameters must be verified from the real response during the Spike; do not assume that a geocoding parameter is valid for POI search.

For a candidate-oriented request:

- send the complete raw query first;
- if a deterministic city clue is safely identified, evaluate the provider's supported city restriction as an additional constraint, but preserve the raw query and record the applied clue;
- request only the first provider page needed to inspect candidate quality; do not implement provider pagination in v0.2A;
- capture provider ordering, not a fabricated confidence score;
- use geocoding as a structured-address fallback or comparison path, not as an automatic override of a better POI candidate;
- preserve provider `info`/`infocode` on failures and never record a secret-bearing URL.

The Spike must test whether candidate-oriented POI search actually improves the four known cases before choosing the production strategy. It must be acceptable to conclude that provider data is insufficient and keep geocoding for precise structured addresses.

## 6. Mandatory real API resolver Spike

The Spike is a separate, redacted-output experiment. It must not change the production `/api/resolve-location` route.

Required queries:

| ID | Query | Main question |
|---|---|---|
| A | `深圳北站` | Does the main train-station entity appear, and how do bus/metro/parking/entrance candidates differ? |
| B | `香港城市大学` | Does the Hong Kong entity rank highly, and does the Chengdu false match remain? |
| C | `澜庭酒店 深圳罗湖` | Does a complete query retain the hotel subject plus Shenzhen/Luohu constraints, without degrading to a district? |
| D | `维也纳酒店` | Are multiple legitimate branches returned with enough identifying information? |
| E | one clearly structured precise address | Which path is more reliable for an address-like input, and is geocode a useful fallback? |

For each query run and record, separately for baseline and candidate-oriented search:

- request strategy label (`geocode-baseline` or `poi-candidate`);
- returned count on the inspected provider page;
- provider ordering index;
- candidate `id` only as an internal comparison field;
- name;
- provider `type` and `typecode`;
- province/city/district when present;
- address;
- location;
- whether the result matches the expected region/entity/type clues;
- original provider `info` and `infocode` when the request fails.

Do not record:

- AMap keys;
- complete key-bearing URLs;
- Authorization headers;
- raw payloads in browser-delivered files;
- unnecessary user-query history outside the redacted Spike artifact.

The artifact must make baseline and candidate output comparable by query and provider ordering. It must explicitly distinguish “no result”, “provider error/permission”, “wrong region”, “wrong entity type”, and “multiple plausible candidates”.

## 7. Spike questions and decision criteria

The Spike must answer:

1. **深圳北站**: Is the train station present? Are related transport/parking/entrance places distinguishable by `type`/`typecode` and address? Does candidate search preserve the parent entity?
2. **香港城市大学**: Is the Hong Kong candidate reliably in the first few results? Is the Chengdu result absent, lower-ranked, or still present? Does the key permit the expected Hong Kong coverage?
3. **澜庭酒店 深圳罗湖**: Does the provider return a Shenzhen/Luohu hotel candidate when the complete query is preserved? Does any result collapse to an administrative district or unrelated place?
4. **维也纳酒店**: Are multiple branches returned with city/district/address sufficient for user choice? Is “one result” actually safe to confirm?
5. **Structured address**: Does geocoding beat POI search for exact address-like input? Can the production resolver retain geocode as an explicit fallback without hiding candidate ambiguity?

Strategy decision is evidence-based per query class, not a universal “POI always wins” rule. If candidate search does not improve a case, record `NEEDS_MORE_DATA` or keep the current path for that case rather than adding speculative filtering.

## 8. Candidate contract

The production-facing candidate model should hide AMap raw response details:

```ts
LocationCandidate {
  id: string;
  name: string;
  placeType: string | null;
  typeCode: string | null;
  city: string | null;
  district: string | null;
  address: string | null;
  longitude: number;
  latitude: number;
  source: "poi" | "geocode";
}
```

Null semantics are explicit for provider-missing type, typecode, city, district, or address. Coordinates are required for a selectable candidate; malformed candidates are discarded with a safe internal diagnostic and cannot break the whole response.

The UI must not depend on AMap-specific field names. `typeCode` may be retained in the server/domain object for deterministic comparison and diagnostics, but it is not a primary user-facing field.

## 9. Resolution state model

Minimal public response direction:

```ts
LocationResolutionResponse {
  query: string;
  status: "confirmed" | "needs_confirmation" | "not_found";
  resolvedLocation: LocationCandidate | null;
  candidates: LocationCandidate[];
  error: { message: string; info: string | null; infocode: string | null } | null;
}
```

Contract rules:

- `confirmed`: `resolvedLocation` is present; `candidates` may contain the evidence set; browser may show the confirmation state but must still display the selected entity/type.
- `needs_confirmation`: `resolvedLocation` is null; candidates are ordered by deterministic evidence/provider order and no candidate is selected by default.
- `not_found`: `resolvedLocation` is null and candidates is empty; this is a safe failure, not a fallback to a partial clue.
- Provider/API failures preserve safe `info` and `infocode` values where available. Public messages must not include keys, full provider URLs, stack traces, or filesystem paths.
- Existing confirmed-search validation remains the authority for the center/candidate pair. Search must not run until a candidate is confirmed.

Compatibility direction, subject to implementation review:

- keep `POST /api/resolve-location` and its `{ query }` request shape;
- add `status`, `candidates`, and nullable `resolvedLocation` to the response;
- retain the existing resolved fields for a confirmed candidate where possible;
- do not expose a second raw-provider endpoint;
- keep `POST /api/search` browser input free of API key, arbitrary keyword, arbitrary type, or provider internals.

## 10. Deterministic matching and ranking principles

This is evidence ordering, not an ML confidence system:

1. Reject malformed candidates and candidates with invalid coordinates.
2. Preserve provider ordering as the final tie-break and diagnostic field.
3. Prefer exact/normalized subject-name matches over weak address-only matches.
4. Reward explicit city and district clue matches; penalize explicit region conflicts.
5. Reward compatible place-type clues. For `深圳北站`, a train-station type is evidence for the main intent; bus/metro/parking/entrance types remain visible related candidates rather than silently becoming the answer.
6. Penalize candidates whose name/address clearly conflicts with a subject or region clue.
7. For multi-clue queries, require subject and region evidence together when both are present.
8. Never promote a candidate only because it is the sole result.
9. Never delete English or Chinese candidates merely because their display language differs from the query.
10. Do not create blacklists, regular-expression store lists, ontology graphs, AI labels, or manually curated POI exceptions.

Fast confirmation is allowed only when there is no material conflict in subject, region, type, or structured-address evidence. Otherwise return `needs_confirmation`, even if there is one candidate.

## 11. Confirmation UX and state changes

The post-Spike implementation should use an inline candidate list, not a modal:

- candidate list first screen: at most about five candidates;
- default selection: `NONE`, never the first candidate;
- each item: name, place type, city/district, address;
- do not lead with provider id, raw typecode, or coordinates;
- selected candidate is visibly distinct and keyboard accessible;
- a separate confirm action creates the `resolvedLocation` used for Nearby Search;
- unresolved/ambiguous state blocks Nearby Search and explains what the user must choose or change;
- confirmed display prioritizes name → place type → city/district → address; coordinates become tertiary.

The existing two-stage flow remains. The change is from “one parsed location” to “resolve candidates → user confirms one entity → search”. No map or visual redesign is included.

## 12. Query mutation and stale-state rules

The accepted stale behavior remains mandatory:

- changing `query` invalidates candidates, selected candidate, resolved location, and nearby results;
- changing query during resolving/searching follows the current disabled/invalidating behavior and cannot leave an old center usable;
- changing from `香港城市大学` to another query must never retain a Hong Kong candidate;
- changing a query after a candidate is selected must require a fresh resolution;
- `POST /api/search` continues to validate that `center` exactly matches the confirmed resolved location.

## 13. Fallback strategy

Fallback order is explicit and safe:

1. Candidate-oriented place search, when the query is place/entity-like and the provider returns usable candidates.
2. Existing geocode path for structured address-like inputs or when the candidate path has a provider capability error, but only after the result passes region/type/subject validation.
3. `needs_confirmation` when there are plausible but conflicting candidates.
4. `not_found` when no candidate satisfies the complete intent.

Forbidden fallback:

- drop the subject and search only city/district;
- silently accept a related bus/metro/parking/entrance entity as the requested parent;
- auto-select the first or sole candidate without evidence;
- use another provider or scrape a third-party source.

## 14. API and UI migration strategy

The smallest compatible implementation should be staged as follows:

1. Add domain types and provider mapping for `LocationCandidate` and resolution state.
2. Add a server-side candidate retrieval method to the existing AMap client only after the Spike proves the endpoint/fields; keep the key server-only.
3. Add deterministic normalization/evidence evaluation as pure functions with unit tests.
4. Extend `/api/resolve-location` response while retaining the `{ query }` request.
5. Extend browser state from one resolved object to resolution status, candidates, and selected candidate; preserve stale invalidation.
6. Keep `/api/search` request validation and confirmed-center equality; adapt only the minimum resolved-location shape needed.
7. Add inline selection and confirmation semantics without a modal or visual redesign.

No implementation starts until the Spike results are reviewed and this plan is separately approved for IMPLEMENT.

## 15. Required automated test matrix

Formal implementation must add deterministic tests for:

| Case | Required assertion |
|---|---|
| `深圳北站` | train-station evidence is preferred or ambiguity is surfaced; bus/metro is not silently confirmed as the parent |
| `香港城市大学` | a Chengdu candidate cannot be silently confirmed when Hong Kong clues conflict |
| `澜庭酒店 深圳罗湖` | raw query is preserved; subject is not discarded; district-only fallback is rejected |
| `维也纳酒店` | multiple candidate path; no default first selection |
| structured precise address | normal resolution path; geocode fallback remains available when evidence is compatible |
| one candidate only | candidate count of one does not alone force auto-confirmation |
| no result | safe `not_found` state with no Nearby Search |
| provider error | `info`/`infocode` preserved; no secret-bearing output |
| missing candidate fields | null semantics; malformed candidate isolation |
| query mutation | candidates, selection, resolved center, and nearby results are invalidated |
| confirmed search | only selected candidate center is accepted; mismatched center rejected |
| English/Chinese names | language difference alone does not discard a candidate |

Do not add tests for provider pagination in v0.2A. Do not make assertions against real provider ordering in unit tests; record that behavior only in the redacted real API Spike artifact.

## 16. Real browser acceptance after implementation

Desktop and mobile acceptance must cover:

1. `深圳北站`: user can distinguish train station from bus/metro/parking/entrance candidates by visible type and address; Nearby Search starts only after a valid confirmation.
2. `香港特别行政区九龙达之路香港城市大学`: resolved candidate is in Hong Kong; Chengdu is not silently confirmed; English POIs continue to render.
3. `澜庭酒店 深圳罗湖`: the hotel subject remains visible; a city/district-only result is not presented as success; user can resolve or safely see not-found.
4. `维也纳酒店`: multiple reasonable branches can be selected inline; no first-item auto-selection.
5. Structured address: resolves without unnecessary ambiguity when provider evidence is precise.
6. Query mutation: old candidates/resolution/results disappear after changing the query.
7. Mobile: candidate list is usable without a modal, page overflow, or hidden confirmation action.

## 18. Risks and limitations

- AMap type/typecode may be wrong or incomplete. The UI should expose type as evidence, not claim canonical certainty.
- Hong Kong/overseas coverage or key permissions may differ from Mainland behavior. Record the exact provider error and do not bypass it.
- Candidate-oriented search may improve recall but return noisy related places. `needs_confirmation` is safer than forced ranking.
- Provider ordering can change. Real Spike output is evidence for this version, not a permanent guarantee.
- Structured addresses and POI names may need different provider paths. Do not force one endpoint to serve both.
- A single candidate can still be wrong. Count alone is never a confirmation rule.
- Inline candidate UI adds state transitions and stale-state paths; pure-function tests and browser verification are required.

## 19. Out of scope

- Provider pagination or result pagination beyond the accepted first page.
- Favorites, notes, accounts, login, database, sessions, maps, navigation, hotel prices, OTA, Meituan, scraping, second provider, AI/LLM, embeddings, vector search, autocomplete, or a complete place-candidate platform.
- New categories, category strategy changes, search templates, ranking redesign, cost/rating changes, radius changes, QPS changes, retries, or concurrency changes.
- Static/export architecture changes, deployment/DNS changes, analytics, monitoring SDK, PWA, or native mobile app.
- Name blacklists, regex exception databases, manual POI lists, complex ontology, confidence-model infrastructure, or a general NLP framework.
- Modal candidate picker or broad visual redesign.
