## 1. Goal and stable baseline

Deploy the accepted v0.1B application from localhost to a public HTTPS URL that works on desktop and mobile, without redesigning or changing search behavior.

The stable baseline is already accepted:

- v0.1A: AMap search core, Mainland/Hong Kong coverage, QPS protection, and native distance passed.
- v0.1B: Next.js App Router, server Route Handlers, two-stage location confirmation, category/radius controls, filters, sorting, load more, responsive UI, API-key isolation, functional verification, and visual verification passed.

Deployment is deliberately split:

1. `v0.1C-1 Temporary Production Deployment`: GitHub → Vercel → platform-provided `*.vercel.app` HTTPS URL, followed by production E2E and secret-leak verification.
2. `v0.1C-2 Custom Domain`: only after C-1 passes, add `nearby.durunqian.com` through Vercel and apply Vercel's then-current DNS instructions in Cloudflare.

## 8. Runtime compatibility

Repository inspection supports the following conclusions:

- `app/api/resolve-location/route.ts` and `app/api/search/route.ts` explicitly use the Node runtime.
- `src/server/amap.ts` uses `server-only` and reads only `process.env.AMAP_WEB_SERVICE_KEY`.

- Native Node `fetch` and the existing AMap client are compatible with Vercel's Node Functions model.
- `package-lock.json` supports `npm ci`.
- The current build pipeline is `npm run build`, which first runs `tsc -p tsconfig.core.json` and then `next build --webpack`.
- `next.config.ts` contains a webpack extension alias used by the current source layout; it should remain unchanged for the first deployment.

Vercel should auto-detect Next.js. During import, verify rather than assume:

- framework preset: Next.js;
- install command: default lockfile-based install or `npm ci`;
- build command: the repository's `npm run build`;
- output directory: framework default, not a custom static output;
- production branch: the branch selected during Git preflight;
- Node version: a Vercel-supported version that satisfies Next.js 16 and the lockfile.

No `vercel.json`, Dockerfile, custom output directory, static-export flag, Edge runtime conversion, or duplicate API is currently required.

## 9. Search duration and serverless limits

The accepted `/api/search` path usually takes approximately 4.6–5.3 seconds because eight categories are requested serially with about 500 ms spacing to protect AMap QPS. This behavior must remain unchanged.

Published Vercel Function limits are above this observed duration. Fluid Compute is enabled by default in current Vercel documentation and has substantially more headroom; documentation for non-Fluid Hobby settings also describes a 10-second default with a higher configurable maximum. Therefore the observed search duration is not a planning blocker, but the actual project/account settings and production tail latency must be verified during C-1.

Initial plan:

- deploy without changing QPS protection or search semantics;
- measure real production success/failure and duration through the browser plus platform request logs;
- treat any timeout as a deployment failure, not as permission to reintroduce concurrency;
- only if real evidence shows the platform duration configuration is too low, propose the smallest targeted follow-up, such as an explicit `maxDuration` on `app/api/search/route.ts`, within the selected plan's published limit;
- do not add that configuration preemptively and do not alter the search core in v0.1C.

## 13. Production secret-leak verification

Use a sentinel approach that never echoes the real key:

1. Before configuration, record only a non-reversible fingerprint locally if an exact-value scan is necessary; never store the value or fingerprint in Git/Harness output. Prefer scanning for forbidden variable prefixes and key-bearing URL patterns first.
2. After deploy, inspect page HTML/source, loaded JavaScript asset text, Network request URLs/bodies/headers, API responses, public error messages, and platform logs.
3. Search for these safe indicators rather than printing the secret:
   - `AMAP_WEB_SERVICE_KEY` in client-delivered artifacts;
   - `NEXT_PUBLIC_AMAP`;
   - `restapi.amap.com` combined with a `key=` query parameter;
   - known key-bearing URL patterns with the matched value redacted.
4. If an exact-value comparison is needed, the checker must return only PASS/FAIL and match location, never the value or surrounding text.
5. A hit in any browser-delivered asset, browser request, API response, public error, committed file, or report fails the gate. Revoke/rotate the affected key before continuing.

Expected safe architecture: browser → app Route Handler → AMap. The key exists only as a Vercel server environment variable and as a server-side outbound request parameter.

## 19. Rollback

Use a two-option, low-complexity rollback:

1. Fast platform rollback: retain the last known-good Vercel production deployment and roll back/promote it if the new deployment fails.
2. Source rollback: revert the offending Git commit, rerun `npm test`, `npm run check`, and `npm run build`, then push and allow Vercel to redeploy.

For a custom-domain-only failure, remove/correct only the new DNS record according to the prior captured state and keep the known-good `*.vercel.app` URL available. Do not build blue/green infrastructure.
